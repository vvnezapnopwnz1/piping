# PipeQC — аудит UI: табы, таблицы, кнопки, формы, фильтрация, сортировка

**Дата:** 2026-08-13
**Метод:** скилл `ui-ux-pro-max` (Data-Dense Dashboard профиль) + сплошной обход `app/`, `modules/*/ui/`, `components/`
**Скоуп:** дизайн-система и работа с большими объёмами данных. Функциональные UX-дефекты уже покрыты Track 13 — здесь их нет.

---

## 0. Резюме

PipeQC — это **не дашборд, а рабочее место оператора QC**: 28 экранов, из которых большинство — списки инженерных объектов (спулы, стыки, фланцы, тест-паки, NDE-обязательства). На реальном проекте это десятки тысяч строк.

Интерфейс сейчас спроектирован под демо-объём. Конкретно:

| Что | Состояние | Факт |
|---|---|---|
| Сортировка | **нет нигде** | 0 совпадений `sortBy` / `aria-sort` / `onSort` во всём репозитории |
| Пагинация | **нет нигде** | `components/ui/pagination.tsx` существует, импортирован **0 раз** |
| Серверная выборка | **нет** | `.range()` — 0 использований; `.limit()` — 1, и это `.limit(1)` |
| Липкая шапка таблицы | **нет** | 0 совпадений `sticky` вне `sidebar.tsx` |
| Виртуализация | **нет** | зависимости нет, все строки в DOM |
| Фиксированная колонка идентичности | **нет** | у всех таблиц `overflow-x-auto` + `whitespace-nowrap` на каждой ячейке |
| Фильтрация | **9 разных ad-hoc реализаций** | `useState("")` + `.filter()` подстрокой в каждом экране |
| `MultiSelectFilter` | **мёртвый код** | импортирован 0 раз |
| Табы | **3 параллельные реализации** | Radix `Tabs` (5 файлов), самописные `border-b-2` кнопки (3 файла), «карточки как секции» |
| Формы | **react-hook-form не используется** | `components/ui/form.tsx` импортирован 0 раз; 30 сырых `<select>` против 6 Radix `Select`; 42 `<label>` без `htmlFor` |
| Токены цвета | **обходятся** | 105 хардкодов `slate-*`, 46 `amber-*`, 27 `emerald-*`, 21 `red-*` |
| Пустые состояния | **сырые** | `components/ui/empty.tsx` импортирован 0 раз |

Главный вывод: **проблема не в том, что таблицы «некрасивые», а в том, что у них нет модели работы с данными.** Дизайн-полировка без сортировки/фильтра/пагинации ничего не даст — оператор всё равно не найдёт нужный стык среди 4000.

## 1. Таблицы — корень проблемы

### 1.1 Что есть сейчас

`components/ui/table.tsx` — чистый shadcn-примитив: `<Table>` = `<div overflow-x-auto>` + `<table>`. Он **только про разметку**. Вся логика данных живёт в каждом экране отдельно.

Типичный экран (`modules/construction/ui/erection/erection-readiness-screen.tsx:80`):

```tsx
<Table>
  <TableHeader><TableRow>
    <TableHead>ISO</TableHead><TableHead>Spool</TableHead>…7 колонок
  </TableRow></TableHeader>
  <TableBody>{rows.map((row) => …)}</TableBody>
</Table>
```

`rows` приходит целиком из репозитория без `limit`/`range`/`order`. То же самое в `flange-management-screen.tsx:89`, `weld-progress-screen.tsx:158`, `nde-batch-screen.tsx`, `tracking-*`.

### 1.2 Что ломается на объёме

1. **Оператор не может найти строку.** Нет сортировки, нет фильтра по колонке, поиск — подстрока по 2–4 полям в 9 из 28 экранов, в остальных нет вообще.
2. **Браузер кладётся.** 4000 `<TableRow>` в DOM + Supabase тянет всё одним запросом.
3. **Горизонтальный скролл теряет контекст.** `whitespace-nowrap` стоит на **каждой** ячейке (`table.tsx:99+`), поэтому таблица из 8 колонок уезжает вправо, а колонка `Weld number` уплывает за край — оператор смотрит на цифры, не зная, чьи они.
4. **Шапка уезжает вверх** при вертикальном скролле — на 200 строках уже невозможно понять, что за колонка.
5. **Числа скачут.** Нет `tabular-nums`, нет выравнивания вправо — `TableHead` жёстко `text-left` для всех типов. Колонки вида `{fieldWeldComplete}/{fieldWeldTotal}` визуально «дрожат» между строками.
6. **Статусы — только текст.** 34 × `Badge variant="outline"` со статусом внутри. Никакого цветового кодирования, кроме `ReferenceStatusBadge` (и тот на хардкоде `emerald/amber/zinc`). Нарушает `color-not-only` в обратную сторону: цвета нет вообще, поэтому взглядом состояние не сканируется.
7. **Пустое состояние = серый текст в `colSpan`.** Ни иконки, ни действия («сбросить фильтр», «импортировать»).

### 1.3 Целевое решение: один `DataTable`

Нужен **один** headless-компонент, который берёт на себя сортировку, фильтры, пагинацию, плотность, закрепление колонок и выбор строк. Все 16 табличных экранов переезжают на него.

**Движок:** *(Пересмотрено при реализации.)* TanStack был поставлен и снят. Всё, что нужно этим экранам — `id`, заголовок и функция доступа к значению; `ColumnDef` с его `accessorFn`/`filterFn`/`sortingFn` добавлял слой поверх ~200 строк собственной логики, ничего не убирая. Оставлен свой headless-слой (`components/ui/data-table/`), примитив `components/ui/table.tsx` — слой разметки. Виртуализацию, когда дойдёт черёд, брать `@tanstack/react-virtual` отдельно: она решает задачу, которую своими силами решать не стоит.

**Предлагаемый API:**

```tsx
<DataTable
  columns={weldColumns}          // ColumnDef[] с meta: { align, filter, sticky, tabular }
  data={welds}
  totalCount={total}             // для серверного режима
  state={tableState}             // единый объект: sorting, filters, page, density
  onStateChange={setTableState}  // пишется в URL
  mode="server"                  // "client" для справочников <500 строк
  rowId={(r) => r.weldJointRevisionId}
  onRowClick={setSelected}
  emptyState={<Empty …/>}
  toolbar={<DataTableToolbar …/>}
/>
```

**Обязательные свойства реализации:**

- **Липкая шапка**: контейнер `max-h-[calc(100dvh-<offset>)] overflow-auto`, `thead` → `sticky top-0 z-10 bg-background` (с бордером-тенью при скролле).
- **Закреплённая колонка идентичности**: первая колонка (`ISO` / `Spool` / `Weld number`) — `sticky left-0 bg-background`, с правым бордером. Это решает п.3 выше.
- **Виртуализация** при `rows.length > 100`, иначе обычный рендер (не платить за виртуализацию на справочниках).
- **Плотность** — переключатель `compact 28px / default 36px / comfortable 44px`. Сейчас жёстко `p-2 text-sm` ≈ 37px. Comfortable нужен не для красоты: полевые экраны (`erection/*`, `tracking/*`) работают на планшете, там `44px` — это требование к тач-таргету.
- **Выравнивание и цифры**: `meta.align: 'right'` для числовых, класс `tabular-nums` на числовые и датовые ячейки. Заголовок числовой колонки — тоже вправо.
- **`whitespace-nowrap` оставить дефолтом, но добавить обрезку.** *(Пересмотрено при реализации.)* Однострочные строки одинаковой высоты — обязательное условие для виртуализации и для сканирования глазом; так делают Linear, Retool, AG Grid. Проблема была не в `nowrap`, а в его отсутствии пары: ячейка без `overflow-hidden`/`max-width` расширяется бесконечно и выносит таблицу за экран. Решение — опция `truncate` + `max-w-*` на текстовых колонках.
- **Выбор строк** — чекбокс-колонка + счётчик выбранного + bulk-панель. Сейчас массовые операции сделаны вручную через `Set` (`tracking-barcode-screen.tsx:41`) с сырым `<input type="checkbox">`.

> Замечание: `TableRow` уже получил проп `interactive` (роль `button`, `tabIndex`, Enter/Space, focus-ring). Это правильное направление — `DataTable` должен его использовать, а не заводить свой обработчик клика.

## 2. Фильтрация — отвечаю на вопрос прямо

Вопрос был: отдельный компонент-фильтр или иконка фильтра у каждого столбца?

**Ответ: и то, и другое, но с чёткой иерархией — панель главная, колонка вторичная. Обе пишут в одно состояние.**

Почему не «только иконки у столбцов» (Excel / AG Grid):
- на 12 колонках **не видно, что вообще отфильтровано** — надо просканировать все заголовки в поисках подсвеченной иконки. Это прямое нарушение видимости состояния системы;
- нельзя сбросить всё одним движением;
- нельзя сохранить и передать коллеге;
- на планшете попасть в 16px-иконку в заголовке — мучение.

Почему не «только панель сверху»:
- QC-инженеры приходят из Excel, их модель — «фильтр живёт в шапке колонки». Убрать это — заставить переучиваться;
- панель не масштабируется: 12 фильтруемых полей в тулбар не влезут.

### 2.1 Архитектура

```
┌─────────────────────────────────────────────────────────────────┐
│ [🔍 Поиск по ISO, спулу, стыку…]   [Вид: Мои открытые RT ▾]  [⚙]│  ← Toolbar
│ Фильтры: [Статус: Open, Rejected ×] [Область: A-12 ×] [Сбросить]│  ← Chips
├─────────────────────────────────────────────────────────────────┤
│ ISO ⇅  │ Spool ⇅ │ Стык ⇅ │ WPS ⇅▾ │ Диаметр ⇅ │ Статус ⇅▾    │  ← Header
```

**Слой 1 — Toolbar (`DataTableToolbar`), главный.**
- глобальный поиск (debounce 300 мс) по «идентифицирующим» полям колонки, помеченным `meta.searchable`;
- 2–4 самых частых фасета экрана как `FacetFilter` (мультиселект с чекбоксами и счётчиками — ровно то, чем должен был стать неиспользуемый `MultiSelectFilter`);
- **чипы применённых фильтров** — каждый снимается крестиком, есть «Сбросить всё». Это и есть видимость состояния;
- селектор сохранённых видов (см. 2.3);
- меню видимости колонок + плотность.

**Слой 2 — меню колонки, вторичный.** В `TableHead` — кнопка с иконкой, открывающая одно меню на все операции с колонкой:

```
↑ По возрастанию
↓ По убыванию
✕ Убрать сортировку
─────────────
🔍 Фильтр…            → тип зависит от meta.filter:
                        text | multiselect | number-range | date-range | boolean
─────────────
📌 Закрепить слева
👁 Скрыть колонку
```

Иконка **всегда видима** у сортируемых/фильтруемых колонок (не по hover — на планшете hover нет), в неактивном состоянии `opacity-40`, при активном фильтре — акцентный цвет + точка-маркер.

Ключевое: фильтр, поставленный из меню колонки, **немедленно появляется чипом в тулбаре**. Тогда нет расхождения между двумя механизмами — это один фильтр, показанный дважды.

### 2.2 Состояние фильтров — в URL

Сейчас `useSearchParams` встречается 6 раз на всё приложение, фильтры живут в `useState` компонента. Следствия: не расшарить ссылку, `Назад` теряет фильтр, F5 сбрасывает работу.

Всё состояние таблицы (`sort`, `filters`, `page`, `view`) должно сериализоваться в query-string. Это даёт бесплатно:
- ссылку в чат бригадиру: «вот эти 40 стыков»;
- корректный `Назад` после ухода в карточку записи;
- deep-link из отчётов и уведомлений.

Реализация — либо `nuqs`, либо тонкий свой хук `useTableUrlState` поверх `useRouter`/`useSearchParams` (~60 строк, без новой зависимости).

### 2.3 Сохранённые виды — то, что реально решает объём

Ни фильтр, ни сортировка не спасают, если оператор каждое утро заново собирает свой срез. Нужны **именованные виды**:

- «Мои стыки без WPS»
- «RT открытые > 7 дней»
- «Field welds на области A-12»
- «Спулы To Site без Material Check»

Вид = сохранённый объект состояния таблицы. Хранение: сначала `localStorage` (личные), затем таблица `project_saved_views` с шарингом на проект. Плюс 1–2 предустановленных вида на экран от команды — они же выступают правильным дефолтом вместо «показать всё».

Это единственная мера из списка, которая уменьшает объём данных **до** того, как он попадёт в браузер.

### 2.4 Серверная сторона

Клиентская фильтрация допустима только для справочников (`project-setup/*`, сотни строк). Для рабочих списков нужен серверный режим:

```ts
let q = client.from('v_weld_worklist').select('*', { count: 'exact' })
for (const f of filters) q = applyFilter(q, f)      // eq / in / gte / ilike
q = q.order(sort.id, { ascending: sort.desc === false, nullsFirst: false })
q = q.range(page * size, page * size + size - 1)
```

Сейчас `.range()` не используется ни разу, `.order()` в UI не управляется. Это надо добавить в репозитории `modules/*/infrastructure/*`, а не в компоненты.

Для колоночных фасетов нужны счётчики — отдельный лёгкий запрос-агрегат либо RPC-вьюха на проект.

## 3. Сортировка

Сейчас её нет вообще. Требования:

1. **Клик по заголовку** — цикл `asc → desc → none`. Клик по всей ячейке заголовка, не по иконке (тач-таргет).
2. **Индикатор всегда на месте**: неактивная колонка — бледная `⇅`, активная — `↑`/`↓` акцентом. Иконка занимает место всегда, иначе заголовок дёргается при сортировке (CLS).
3. **`aria-sort="ascending|descending|none"`** на `<th>` — обязателен, сейчас 0 совпадений в репозитории.
4. **Мультисортировка** — Shift+клик, порядок показывается цифрой (`↑1`, `↓2`). Нужна для «сортировать по области, потом по номеру стыка».
5. **Сортировка серверная** в server-режиме, с `nulls last` по умолчанию — иначе «—» всплывёт наверх и займёт первый экран.
6. **Дефолтная сортировка на каждом экране осмысленная**, не порядок вставки: рабочие списки — по «горит/просрочено», справочники — по коду.
7. **Сортировка сохраняется** в URL и в сохранённом виде.

## 4. Табы

### 4.1 Диагноз

Три несовместимые реализации:

- **Radix `Tabs`** — `project-referential-screen.tsx:73`, `execution-reference-tabs.tsx:422`, `extended-reference-tabs`, `tracking-data-analysis-screen`, `documentation/page`. Пилюля (`bg-muted` + `rounded-lg`).
- **Самописные `border-b-2` кнопки** — `welding-quality-tabs.tsx:600+`, `project-geography-tabs.tsx`, `progress-weights-screen.tsx`. Подчёркивание. Никакого Radix: нет ролей `tab`/`tabpanel`, нет стрелок клавиатуры, нет `aria-selected`.
- **Карточки-секции** без табов вообще.

То есть на соседних экранах один и тот же тип навигации выглядит и работает по-разному.

Плюс **вложенность на 2 уровня**: `/admin/project-referential` → 6 табов верхнего уровня → внутри «Welding & Quality» ещё 8 самописных подтабов (Service Classes, Weld Types, WPS, Thickness/Flange, PML, Rework, Joint Categories…). Пилюля внутри пилюли — оператор теряет, где он.

Плюс **состояние таба не в URL** (`activeTab` в `useState`, `project-referential-screen.tsx:32`): нельзя дать ссылку на конкретный справочник, `Назад` из диалога роняет на первый таб.

### 4.2 Что делать

1. **Один компонент, две визуальные роли.** Расширить `components/ui/tabs.tsx` вариантами:
   - `variant="underline"` — навигация по разделам страницы (верхний уровень). Подчёркивание читается как «страницы».
   - `variant="pill"` — переключение среза внутри одного контента (второй уровень, фильтр-подобные переключения).
   Тогда вложенность различима визуально, а не «пилюля в пилюле». Самописные `border-b-2` кнопки удалить — они станут `variant="underline"` и получат бесплатно всю a11y Radix.
2. **Счётчики в табах — оставить**, они уже есть (`Teams ({data.teams.length})`) и это правильно. Оформить как `Badge` внутри триггера, а не текстом в скобках, и добавить `tabular-nums`.
3. **Таб → URL**: `?tab=welding` (и `?sub=wps` для второго уровня). Даёт deep-link из `SetupReadinessPanel` (там уже есть `onNavigateTab` — он станет обычной ссылкой).
4. **Переполнение**: сейчас `TabsList className="w-full overflow-x-auto"` — горизонтальный скролл без индикатора, на узком экране табы просто теряются. Нужны градиенты-подсказки по краям + кнопки прокрутки, либо `overflow` в меню «Ещё ▾» при >6 табах.
5. **Ленивая загрузка контента**: сейчас `ProjectReferentialScreen` монтирует все 6 панелей, каждая тянет свои справочники. Radix `Tabs` умеет размонтировать неактивные — включить, чтобы не было 6 параллельных загрузок на входе.
6. **8 подтабов в `welding-quality-tabs` — это уже не табы.** 1799 строк в одном файле с 8 сырыми `<table>` внутри. Разбить на отдельные модули-справочники и рассмотреть боковой список слева (master-detail) вместо горизонтальной ленты: у справочников список длинный и растёт.

## 5. Кнопки

Базовый `components/ui/button.tsx` в порядке: cva, 6 вариантов, 6 размеров, focus-visible ring, `disabled:opacity-50`. Проблема не в примитиве, а в применении.

1. **Нет состояния загрузки.** Правило `loading-buttons`. Сейчас каждый экран изобретает своё: `{saving ? "Saving…" : "Record flange progress"}` (`flange-management-screen.tsx:120`) — текст меняется, ширина кнопки прыгает, спиннера нет; а `nde-batch-screen` местами не блокирует кнопку вовсе. Нужен проп `loading` в `Button`: спиннер слева, текст сохраняется, `disabled` + `aria-busy`, ширина фиксируется.
2. **Нет иерархии на экране.** На карточках соседствуют несколько `variant="default"` (синих) кнопок — глазу не за что зацепиться. Правило `primary-action`: одно основное действие на экран/карточку, остальные `outline`/`ghost`.
3. **Деструктивные действия не отделены.** `destructive` вариант есть, но удаление/архивирование стоит в общем ряду. Нужен визуальный и пространственный разрыв + `AlertDialog` (компонент есть) на подтверждение.
4. **Icon-only кнопки без `aria-label`** — проверить точечно; при переходе на меню колонок их станет много, правило нужно зафиксировать сразу.
5. **Кнопки в строках таблицы** — размер `sm` (32px) для desktop, но на полевых планшетных экранах нужен `default` (36px) плюс `hitSlop`-паддинг ячейки; иначе промахи на объекте.

## 6. Формы

### 6.1 Диагноз

- **`react-hook-form` в зависимостях, `components/ui/form.tsx` существует — используется 0 раз.** Все формы — россыпь `useState` на поле (в `nde-batch-screen` — 15 отдельных `useState`, в `flange-management-screen` — 8).
- **30 сырых `<select className="h-9 rounded border …">`** против 6 Radix `Select`. Сырой селект не стилизуется, не ищет по вводу (а списки сварщиков/WPS длинные), выглядит инородно.
- **42 `<label>` без `htmlFor`.** Часть обёрнута вокруг инпута (это валидно), но паттерн `<label className="text-sm">Report number<Input …/></label>` (`flange-management-screen.tsx:115`) даёт нестабильную a11y и нулевой контроль над версткой.
- **Ошибки валидации — в тостах.** `toast.error(Object.values(result.errors)[0] ?? "Check the form.")` — показывается **одна** ошибка, **не у поля**, и исчезает через 4 секунды. Нарушает `error-placement`, `focus-management`, `error-summary`. Оператор с формой на 12 полей не поймёт, что чинить.
- **Нет `zod`-резолвера в UI**, хотя `zod` в зависимостях, а доменные правила уже описаны в `modules/*/domain` и `application` (например `describeWeldProgressGate`).
- **Нет автосохранения черновиков** в длинных формах (`form-autosave`), а формы длинные и заполняются на объекте.

### Кто сейчас редактируется

Две связанные дыры, найденные при разборе рабочего процесса.

**Свёрнутая строка спула** показывала выбор как `text-xs` рядом с подписью — единственный след выбора из тысяч был набран как подпись к картинке. Теперь это заголовок: `font-mono text-xl/2xl font-bold`, карточка в акцентной рамке, рядом ревизия и ISO.

**Смена стыка** сообщалась изменением одного слова в заголовке карточки. Поля не двигались, позиция не менялась — оператор, уже начавший вводить данные, не имел причин считать, что цель сменилась. На экране, который пишет сварочные свидетельства, это не неудобство, а запись на чужой стык.

`ChangeHighlight` даёт четыре сигнала, потому что ни один не работает во всех случаях:

| Сигнал | Закрывает |
|---|---|
| Вспышка карточки + акцентное кольцо (900 мс) | взгляд на форме |
| Прокрутка к форме, если она ушла за экран | клик по строке в длинном списке — вспышку никто не увидит |
| `IdentityHeadline` с номером стыка крупно | «а что я вообще сейчас редактирую» |
| `aria-live="polite"` | скринридер |

Вспышка живёт в отдельном перемонтируемом оверлее — повторяется на каждой смене, не трогая состояние формы, фокус и позицию прокрутки. `prefers-reduced-motion` снимает анимацию и плавную прокрутку, заголовок и объявление остаются.

Вторая половина связки — сама строка: `data-[state=selected]` теперь сильнее hover (`bg-primary/10`, `font-medium`, полоса `inset 3px` по ведущему краю, переживающая горизонтальную прокрутку).

Применено к трём формам, которые перенацеливаются из worklist: цеховые стыки, полевые стыки, фланцы. Тест не даёт новой форме объявить смену цели одним `<CardTitle>Record {…}</CardTitle>`.

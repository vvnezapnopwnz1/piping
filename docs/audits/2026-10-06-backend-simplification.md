# Бэкенд PipeQC: что упростить и в каком порядке

Дата: 2026-10-06. Статус: сводный анализ и предложение порядка работ. Реализацией не является.

Источники:
- обзор свежих изменений (Claude);
- ответ второго агента об упрощении бэкенда;
- проверка обоих по текущему коду в тот же день.

Всё ниже относится к рабочему дереву ветки `docs/pipeqc-landing-spec`, которое ещё не закоммичено.

## Цель

1. **Одно правило — одно место.** Чтобы изменить бизнес-правило, достаточно правки в одном файле.
2. **Отказ объясняет сервер.** Пользователь видит конкретную причину, клиент её не вычисляет заново.
3. **Состояние объекта видно сразу.** Почему спул или пакет не готов, можно понять без расследования по таблицам.
4. **Каждый шаг упрощения уменьшает код.** Новые механизмы допустимы, только если они заменяют несколько старых.

## Как связаны Fabrication, Erection, NDE и Project Setup

```
Project Setup (справочники)          Engineering / Spooling
PML, WPS, сварщики, классы,          спулы, ревизии, BOM,
подрядчики, PDS-зоны                 стыки, опоры
        │ допустимые значения                 │ что строить
        ▼                                     ▼
              Construction: Fabrication + Erection
              команды записывают факты работ
                        │ запись сварки создаёт обязательства
                        ▼
              Quality: NDE / PWHT
              обязательства → партии → результаты
                        │
                        ▼
      fabrication_spool_projections — статус спула
      (11 триггеров на таблицах Engineering, Construction и Quality;
       отсюда читают Fabrication, Erection и графики)
```

- **Project Setup** — источник допустимых значений. Construction только читает их и сверяет, а сам ничего в справочниках не меняет.
- **NDE** — отдельный владелец обязательств, партий и результатов. Обязательства создаются при записи сварки, а их открытые счётчики блокируют QC Release и RFT.
- **Точка схода** — `fabrication_spool_projections`. Это единственное место, где уже собраны факты всех четырёх модулей. Изменения в неё приходят через триггеры, то есть их не видно из кода команд.

Отсюда вывод: **начинать надо с этой проекции, а не с отдельных экранов.** Пусть она отдаёт не только флаги `is_ready` / `is_rft`, но и коды причин:
```
blockers = ['welds', 'nde', 'pwht', …]
```
Тогда из одного столбца читают все потребители:
- экраны Fabrication и Erection;
- переходы в NDE;
- графики.

Клиентские копии правил (B6, B7) удаляются. Образец в проекте уже есть: `isometric_readiness.blocker_counts` в `20260813094000_test_pack_readiness.sql` — так устроена готовность Test Pack.

Project Setup и NDE в этом шаге не перестраиваются. Меняется только то, как их влияние видно в статусе спула.

## Ответ второго агента: где согласны, где нет

Согласны:
- у каждого правила один владелец;
- статус и причины считает сервер;
- команда принимает минимум данных;
- текущую схему должно быть можно прочитать целиком;
- DB-тесты изолированы.

Поправки:
- **Tracking — не главный пример несогласованности.** Его механизм строже общего и опирается на ключи событий устройств. Исправлять стоит общий `claim_command_receipt` (B9), а не переводить оба модуля на новый протокол.
- **Payload можно сокращать сразу.** «Проверка совместимости» уже сделана: старый формат используют только два скрипта демо-данных.
- **Декларативные схемы — это смена инструмента.** Сначала хватит генерируемого снимка схемы (B10).
- **Карта бэкенда отдельным проектом не нужна.** Достаточно схемы связей выше и снимка схемы.
- **Чего во втором ответе нет:** чтения в обход RLS (B2), ручных JSON-контрактов (B3), лишней постраничной загрузки (B4), сборки Test Pack на клиенте (B5).
- Оценка «6/10» у второго агента — тоже экспертная догадка, а не измерение.

## Правила для всех агентов

Эти правила стоит добавить в `AGENTS.md` (его читают Codex и agy) и в `CLAUDE.md`.

1. Чтение — обычный `select` из таблиц или view с `security_invoker = true`, типы генерируются. RPC используются только для команд записи.
2. Права проверяются только в RLS-политиках, сужающие — в `as restrictive`. Функции `SECURITY DEFINER` для чтения данных пользователю не создавать.
3. Команда принимает ID, остальное сервер выводит из связей. Формат у команды один: при смене формата всех вызывающих обновляют в той же правке, без слоя совместимости.
4. Правило допуска живёт в SQL-команде или проекции. Клиент показывает причину от сервера (код → подпись) и не пересчитывает её.
5. Экран одного объекта читает один или несколько view и не собирает данные из десятка запросов.
6. Постраничная загрузка и курсоры — только после замера реального объёма.

Правило 2 совпадает с `supabase-postgres-best-practices` (`references/security-rls-performance.md`): функции `SECURITY DEFINER` обходят RLS, поэтому их держат в непубличной схеме и отзывают у них `EXECUTE`.

## Нужен ли отдельный скилл

Скилл, который сам расставит всё по местам, не нужен. Порядок держат три вещи:

1. **Правила выше** — в `AGENTS.md` и `CLAUDE.md`. Эти файлы агенты загружают сами, а скилл исполнитель может не вызвать.
2. **Автоматические проверки в `npm run verify`.** Они работают независимо от того, прочитал ли агент правила. Например:
   - pgTAP-тест сравнивает список читающих `SECURITY DEFINER`-функций в `public` с разрешённым списком;
   - тест проверяет, что каждая команда использует общий механизм защиты от повтора.
3. **Установленный `supabase-postgres-best-practices`.** В планах, затрагивающих `supabase/`, требовать от исполнителя загрузить его.

Свой проектный скилл имеет смысл, только если правила перерастут одну страницу.

## Порядок работ

Каждый шаг — отдельный небольшой план для исполнителя. Шаг считается сделанным, когда `verify` зелёный, а итог в строках кода отрицательный.

| Шаг | Что | Закрывает | Модули |
|---|---|---|---|
| 0 | Закоммитить текущее состояние частями (оболочка/навигация, Fabrication+Erection, Test Pack, Material Check с миграцией, презентации отдельно), чтобы упрощение было видимой правкой | — | все |
| 1 | Правила в `AGENTS.md` / `CLAUDE.md` и автоматические проверки | новая сложность | все |
| 2 | Упростить Material Check | B1–B4, B8 | Fabrication, Erection, Project Setup (PML) |
| 3 | Коды причин в статусе спула; удалить клиентские копии правил | B6, B7 | Fabrication, Erection, NDE/PWHT |
| 4 | Снимок текущей схемы: сначала Construction, Quality/NDE, Project Setup | B10 | эти три |
| 5 | Сверка данных в общем механизме защиты от повтора | B9 | все команды |
| Позже | View для Test Pack (B5), изоляция DB-тестов (B11), порядок в `scripts/` (B12) | | |

Сейчас не делать:
- переписывать все команды на новый общий протокол;
- переходить на декларативные схемы;
- затевать один большой рефакторинг бэкенда.

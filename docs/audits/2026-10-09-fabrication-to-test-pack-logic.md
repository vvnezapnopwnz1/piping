# От цеха до test pack: что работает, что не закончено, почему UI сбивает с толку

Дата: 2026-10-09. Статус: анализ перед планом. Код, схема и данные не менялись.

> **Решение владельца в тот же день:** не усложнять. Новые функции из §6 (Q2, Q3, Q6) и ворота L8–L10 отклонены. Остальные находки — гипотезы. Их проверяет пошаговый проход по мануалу: `docs/superpowers/specs/2026-10-09-e2e-walkthrough-design.md`.

Начато в сессии Codex (`codex-session-01a120b7-…md`), которая остановилась посреди анализа без итогового отчёта. Её находки перепроверены и дополнены по живой базе локального стенда: определения view и функций читались через `pg_get_viewdef` / `pg_get_functiondef` в транзакциях `READ ONLY`. Последняя применённая миграция — `20261007090000`. Unit-тесты: 638 из 638 (прогон Codex). pgTAP не запускался, стенд не сбрасывался.

## Коротко

1. **Цех сделан хорошо.** Material Check → сварка → NDE/PWHT → QC Release → покраска → Final QC → Laydown: каждый шаг проверяется на сервере и не пропускается.
2. **Ломается граница «цех → монтаж → испытание».** Готовность к испытанию (RFT) считается по датам этапов, а не по фактам. На стенде `SP-1001-A` показана как «Готова к испытанию» при `0/2` монтажных стыках и `0/1` монтажной опоре.
3. **Сервер мягче интерфейса.** Старт испытания не проверяет ни RFT, ни заглушки. Восстановление фланцев Y/Z не ждёт испытания. Порядок шагов соблюдает только клиент, который сам вычисляет состояние процесса (правило 4 из CLAUDE.md).
4. **Test pack не доведён до сдачи.** Нет результата испытания, нет пути «утечка → ремонт → повтор», нет состояния «закрыт». Изменение ревизии ISO после проверки линии или испытания ничего не помечает.
5. **UI неправильный по двум причинам.** Первая — экран честно показывает несовместимые факты, которые выдаёт сервер, и компоновкой это не исправить. Вторая — у одного пакета четыре входа (Dashboard, Builder, Explorer, Pressure Test) и 22 страницы под `/testpack`.

## 1. Как процесс должен работать

Здесь три разных решения, принимаемых разными людьми по разным доказательствам. Сейчас они смешаны в одно слово RFT.

| Решение | Объект | Кто | Доказательства |
|---|---|---|---|
| **Катушка изготовлена и выпущена из цеха** | spool revision | QC цеха | материалы прослежены, все цеховые стыки сварены, цеховые NDE/PWHT закрыты, подписан QC Release (QC-13), покраска/DFT, Final QC, Laydown |
| **Линия механически завершена** | spool → ISO | мастер монтажа + QC | катушка на площадке и смонтирована, **каждый** монтажный стык сварен/собран, **каждая** монтажная опора установлена, монтажные NDE/PWHT закрыты, фланцы собраны |
| **Контур допущен к испытанию** | test pack | тест-инженер + QC заказчика | все ISO механически завершены, проверка линии (walkdown) выполнена, X-замечания закрыты, заглушки установлены по списку |

После допуска процесс идёт по пакету: **испытание** (старт → результат) → **восстановление Y** → **пусконаладка** → **восстановление Z** → **пакет закрыт и сдан**. Формула Easy Piping, которую мы копируем (`docs/research/test_pack_appendix.md`):

```
ISO_COMPLETE = все катушки welded&bolted И supported
QC_RELEASED  = все стыки NDE released И PWHT released
ISO_RFT      = QC_RELEASED И ISO_COMPLETE И LINE_CHECK_DONE И все X закрыты
TP_RFT       = все ISO пакета RFT
```

Что должно входить в test pack с точки зрения бизнеса. Пакет — это то, что подрядчик сдаёт заказчику, поэтому в комплекте должно быть:

- **Определение:** номер, система/подсистема, класс/среда, испытательная среда и давление, границы контура.
- **Состав:** ISO с действующими ревизиями. Спулы и стыки выводятся из ISO.
- **Доказательства готовности:** журнал сварки, NDE/PWHT по каждому стыку, проверка линии, X-замечания с закрытием.
- **Подготовка:** список заглушек (blinding), подтверждение установки.
- **Испытание:** даты, результат, протокол или акт (номер, свидетель).
- **Восстановление:** фланцы Y/Z (дата, номер отчёта, бригада, бирка).
- **Закрытие:** дата сдачи пакета.

Сейчас есть всё, кроме результата испытания и закрытия; см. L7.

## 2. Что работает (проверено)

- **Инженерные данные:** импорт Spoolgen, ревизии ISO с решениями, revision workbench.
- **Цех.** Все шаги проверяются на сервере. `release_quality_record` отказывает с конкретной причиной: материалы, стыки, опоры, NDE, PWHT, дата раньше изготовления. Покраска требует Sent to Paint и проверяет DFT по матрице и номер формы W10P. Laydown требует Final QC. Сварка проверяет WPS и квалификацию сварщика.
- **NDE:** обязательства по матрице, партии, результаты, ремонт/tracer, штрафные выборки.
- **Перемещения:** события с идемпотентностью, корректировки только компенсацией.
- **Монтаж:** этапы To Site → Erected → Welded/Bolted → Supported идут строго по порядку, RFT вручную не ставится (`PQC55`).
- **Test pack.** Работают состав с блокировкой после начала работ, Line Check с X-замечаниями, Item Clearance, назначение Blinding только для RFT-пакета (`PQT06`). Пусконаладка блокируется, пока не восстановлены все Y-фланцы (`PQT16`). Даты монотонны, печать заявок есть.
- **Во всех командах:** идемпотентность, аудит, RLS, `security_invoker` view.

## 3. Что не закончено или неверно

Важность: **высокая** — система выдаёт неверный ответ о готовности или допускает недопустимое действие; **средняя** — пробел в процессе сдачи; **низкая** — неточность.

Не проверяются ни `field_weld_complete = field_weld_total`, ни монтажные опоры. ## 4. Почему UI/UX сейчас неправильный

**U1. Экран показывает несовместимые факты, потому что их выдаёт сервер.** В списке монтажа рядом стоят «Готова к испытанию», «Монтажные стыки 0/2» и «Опоры на монтаже 0/1». Пользователь перестаёт доверять статусам. Это не исправить компоновкой: сначала L1–L3.

**U2. У одного пакета четыре входа.** Под `/testpack` 22 страницы:

| Страница | Что делает |
|---|---|
| Dashboard | счётчики |
| Builder, 693 строки | определение и состав — **дублирует** вкладки workbench |
| Explorer | это и есть новый `TestPackWorkbench`: список + drawer с вкладками Definition / Composition / Readiness / Workflow |
| Pressure Test | 5 разделов, у каждого preparation / progress, ещё 11 маршрутов поперёк пакетов |

Одну и ту же работу (например, назначить заглушки) можно найти в двух местах с разной подачей. Принцип «объект выбирается один раз» из D-оболочки здесь не выдержан.

**U3. Клиент сам решает, что можно делать.** Состояния Y / пусконаладки / Z вычисляет TypeScript, а сервер разрешает больше (L4, L5). Пользователь видит «заблокировано», а API пропустит. Если клиент ошибётся в другую сторону, кнопка будет активна, а сервер откажет без объяснения.

**U4. Счётчики Dashboard названы неверно.** «Ready» считает **выполненные** работы (`result_id !== null`), «Ongoing» — всё остальное. В Easy Piping Ready означает «можно выдать, ещё не выдано», Ongoing — «выдано, не выполнено». Карточка «Ongoing / blocked» смешивает заблокированные пакеты с испытываемыми. В Release backlog причиной блокировки всегда показывается только число X-замечаний, даже если пакет держат стыки или NDE.

**U5. Текст для разработчика вместо текста для оператора.** «Database-backed release tracking and pressure-test workflow.», «Canonical order: RFT → Blinding → …». Test pack пока целиком на английском, хотя остальное приложение переведено.

**U6. Блокер показан не там, где начинается проблема.** Не изготовленная катушка в списке монтажа получает причину «Сварка / сборка не записана», а не «не выпущена из цеха» (следствие L9).

**U7. Модуль нельзя увидеть.** На демо-проекте нет пакетов (L13). Ни владелец, ни покупатель не видят самую сложную часть продукта.

## 5. Как лучше

Рамка та же, что у цеха и монтажа: **список объектов → выбранный объект → его состояние → одна доступная операция → подтверждённый результат**.

1. **Сначала правила, потом экраны.** На сервере вводится одно понятие «механически завершено» (катушка и ISO): монтажные стыки, монтажные опоры, монтажные NDE/PWHT, этапы. Его используют и RFT катушки, и RFT ISO. Опоры получают shop/field. Команды испытания и восстановления проверяют свои предусловия. Готовность фиксируется при старте испытания.
2. **Одна проекция состояния пакета.** View `test_pack_workflow` (security_invoker) отдаёт текущий шаг, доступную операцию и коды причин блокировки по ISO, как `blocker_counts`. Клиент только переводит коды в подписи; `test-pack-workflow-model.ts` и клиентский `derivePressureTestState` удаляются.
3. **Один пакет — одна рабочая область.** Шкала пакета повторяет шкалу катушки: Состав → Готовность (причины по ISO со ссылками в цех, монтаж, NDE) → Проверка линии и X → Заглушки → Испытание → Y → Пусконаладка → Z → Сдан. По умолчанию открыт следующий шаг, доказательства рядом. Builder, Explorer и Pressure Test становятся алиасами одной страницы.
4. **Работы поперёк пакетов — одна вкладка.** Мастеру нужна выдача по бригаде: какие проверки линии, заглушки или восстановления можно выдать сегодня. Это одна таблица «Работы» с фильтром по виду и состоянию (Можно выдать / Выдано / Выполнено) и печатью заявки, а не 11 маршрутов.
5. **Dashboard — только счётчики со ссылками** в отфильтрованный список, как на обзоре проекта. Правильные Ready/Ongoing.
6. **Демо-пакет.** В `demo:showcase` добавить 2–3 пакета на разных шагах: заблокирован, готов к заглушкам, испытан и ждёт Y.

Пункты 1–2 — изменение правил на сервере, 3–6 — упрощение интерфейса. Они не добавляют функций, кроме того, что решит владелец по §6.

## 7. Скиллы для следующих шагов

- `supabase-postgres-best-practices` — обязателен по CLAUDE.md для всего, что меняет `supabase/`: view, команды, RESTRICTIVE-политики.
- `domain-driven-design` — границы катушки, ISO и пакета, инварианты «механически завершено» и «допущен к испытанию», в каком агрегате живёт правило.
- `jobs-to-be-done` — работы ролей: мастер цеха, мастер монтажа, QC, тест-инженер, заказчик на сдаче. Отсюда шкала пакета и вкладка «Работы».
- `ux-heuristics` + `design-everyday-things` — проверка экрана пакета: видимость состояния, предотвращение ошибок, понятные причины блокировки.
- `test-driven-development` — сначала pgTAP-тесты, которые сейчас падают на L1–L6 (на изолированном `.pgtap-stack`, не на живом стенде).
- `writing-plans` — оформить план после ответов на §6.
- По желанию `37signals-way`: ограничить объём (appetite) и не дать плану разрастись — цель редизайна в упрощении.

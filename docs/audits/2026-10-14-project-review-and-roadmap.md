## 0. Коротко

1. **Ядро сделано честно.** Сервер владеет командами: транзакции, идемпотентность, аудит, RLS, append-only история. Цех проходит мануал целиком. Прогон UPG-1 прошёл 8 недель и ~1 600 действий через настоящие команды.
2. **Мануал уже решает большую часть открытых находок.** L1, L2, L4, L5, F3 и F7 нарушают §29 и §30 досье. Это ошибки, а не новые функции: их можно исправлять, не дожидаясь полного прохода.
3. **Снаружи видна версия двухмесячной давности.** Production собирается из `main`, а `main` отстаёт на 83 коммита (последний — 17.08). На hosted нет русского, нет нового дизайна и нет минимум 5 октябрьских миграций. Hosted на бесплатном тарифе засыпает через 7 дней простоя. Зависание «Loading PipeQC…» не исправлено, утёкший legacy-ключ не отозван. Письма для КЗ-подрядчиков уже готовы к отправке.
4. **Объём не проверен.** Самый большой прогон — около 500 стыков. Реальный пилот — 5–15 тыс., проект EPC — 100+ тыс. Списки по проекту без пагинации молча обрезаются на 1 000 строк. Импорт идёт одной транзакцией через построчные триггеры.
5. **Выход для заказчика почти пуст.** Из 22 отчётов мануала есть 2, своих. Русской исполнительной документации (журнал сварки, реестр NDE, акт испытания) нет. `audit_events` пишут 23 миграции, а читает их ни один экран.
6. **UI:** цех, монтаж и настройка проекта упрощены. Тест-пакет — самый сильный модуль по домену — по-прежнему открывается из четырёх входов и 22 страниц. NDE не переделан.
7. **Порядок работ:** выпуск и безопасность → правильность по мануалу → сквозной проход UPG-1 → тест-пакет и NDE → данные на входе и объём → документы на выходе → площадка пилота.

## 4. System design (отдельно, по рамке system-design)

### 4.1. Требования

**Функциональные:** мануал §1–20; сквозная нить — справочники → спулинг → цех → NDE → монтаж → тест-пакет → испытание → сдача.

**Нефункциональные** (нигде не записаны; предлагаю зафиксировать):

| Требование | Цель для пилота | Почему |
|---|---|---|
| Изоляция | проект, субподрядчик, PDS — только RLS | уже так, держать |
| Правильность производных состояний | сервер — единственный владелец | QC-система, на её статусах подписывают акты |
| Прослеживаемость | кто, когда, по какому документу — по любому объекту, видно в UI | приёмка заказчиком, споры |
| Доступность | 99,5 % в рабочее время (≈3,6 ч простоя в месяц) | ввод в конторе участка по формам W-24 и W-23 |
| RPO / RTO | ≤ 1 ч / ≤ 4 ч | потеря дня ввода по 30 бригадам — неделя пересверки бумаги |
| Резидентность данных | КЗ: данные сварщиков в Казахстане (уточнить у юриста) | 152-ФЗ и закон РК о персональных данных |
| Язык | RU, затем KK | пилот |
| Связь на площадке | онлайн из конторы; офлайн — по запросу пилота | мануал описывает ввод с бумажных форм (§12.4–12.7); офлайн КПК там отдельная функция §10.5 |

### 4.2. Оценки на салфетке

| Масштаб | ISO | Катушки | Стыки | Тест-пакеты | Пользователи |
|---|---|---|---|---|---|
| UPG-1 (проверено) | 40 | ~100 | ~500 | 6 | 1 скрипт |
| Пилот: монтажный субподрядчик на одной установке | 300–800 | 1,5–4 тыс. | 5–15 тыс. | 20–60 | 10–30 |
| Проект EPC целиком | 3–5 тыс. | 20–30 тыс. | 100–150 тыс. | 200–300 | 100–200 |

Для сравнения: WebJoint заявляет 11 тыс. и 20 тыс. стыков на НПЗ.

- **Запись.** 30 сварщиков × 3 стыка в смену ≈ 90 стыков в день. Каждый даёт около 12 строк (корень, заполнение, облицовка, обязательства, результаты, аудит), итого ≈ 1–2 тыс. строк в день.
- **Чтение.** 30 пользователей × 300 запросов в день ≈ 0,1 rps в среднем, 5–10 rps в пик конца смены.
- **БД.** 150 тыс. стыков × 12 строк × ~1 КБ с индексами ≈ 2 ГБ на проект EPC; пилот — 150–300 МБ.
- **Файлы.** ISO в PDF 0,5–1 МБ × 4 тыс. × 2 ревизии ≈ 4–8 ГБ, плюс заключения и фото.
- **Тариф.** Бесплатный (500 МБ БД, 1 ГБ файлов, засыпает) пилот не выдержит по файлам и надёжности. Pro (8 ГБ БД, 100 ГБ файлов, ежедневные бэкапы, PITR опционально) — с запасом.

**Вывод:** нагрузка не проблема ни на одном масштабе. Узкие места — в пути чтения и в импорте (§4.3), а не в мощности.

### 4.3. Текущая архитектура

```
Браузер (Next.js 16, всё "use client", сессия в localStorage)
  ├─ чтения: PostgREST select из таблиц/view (RLS)     ← лимит 1 000 строк
  ├─ команды: rpc(...) → SQL-функции в транзакции       ← statement_timeout authenticated
  ├─ файлы: Storage (спулинг-импорт, брендинг)
  └─ отчёты: xlsx/jsPDF в браузере, без хранения
        │
Supabase: Auth · PostgREST · Storage   (Edge Functions, очередей, кэша нет)
        │
Postgres 17: 103 таблицы · 34 view · 157 функций (125 SECURITY DEFINER) · 72 триггера
  projections: fabrication_spool_projections ← 11 построчных триггеров
  audit_events (пишется, не читается) · command_receipts (идемпотентность)
```

Модульный монолит плюс Postgres как источник истины — правильный выбор для такого домена (AD-01, AD-02). Очереди, кэш и шардинг не нужны.

**Разбор трёх мест, где система сломается раньше, чем кончится мощность:**

1. **Путь чтения.**
   - Проектные списки без пагинации (`nde_obligations`, `spool_erection_readiness` по проекту) обрезаются на 1 000 строк. Сортировка на клиенте идёт после обрезки. Пользователь не видит часть обязательств и не знает об этом.
   - Список катушек цеха уже на курсорах (до 100 строк), то есть подход в коде разный.
   - Политики вызывают `current_user_has_capability(project_id, …)` на каждую строку. На 10 тыс. строк это 10 тыс. вызовов.
   - Правило 6 из CLAUDE.md («без пагинации без замера») здесь не нарушено по духу: замер и есть лимит 1 000.
   - Решение: серверные фильтры и счётчики во view, пагинация только для проектных списков, данные одной катушки или одного пакета — по-прежнему одним запросом.
2. **Импорт.**
   - Файл `weld.txt` в 4 МБ — это 20–40 тыс. строк.
   - Применение идёт одним RPC в одной транзакции. Каждая вставка в `weld_joint_revisions` и соседние таблицы запускает пересчёт проекции своей катушки.
   - На hosted у роли `authenticated` короткий `statement_timeout` (по умолчанию в Supabase 8 с).
   - Решение: замерить на синтетическом UPG-20k (генератор уже есть). Затем либо применять по ISO порциями (`import_jobs` уже хранит строки), либо отложить пересчёт проекции до конца транзакции (statement-level триггеры или одна функция пересчёта по затронутым катушкам).
3. **Эксплуатация.**
   - Бесплатный тариф засыпает, PITR нет, мониторинга нет, CI нет.
   - Релиз — ручной merge в `main`, которого два месяца не было.
   - Hosted в us-east-1, а данные сварщиков КЗ, вероятно, должны лежать в КЗ.
   - Решение: CI на PR, релиз раз в фазу, Pro или self-hosted Supabase в КЗ-облаке, Sentry плюс логи Supabase, отрепетированный restore.

### 4.4. Оценка: 5/10

| Область | Оценка | Почему |
|---|---|---|
| Требования | 4 | Функциональные — мануал; нефункциональные нигде не записаны |
| Оценки объёма | 2 | Ни одной; проверено ~500 стыков при целевых 5–150 тыс. |

### Фаза 6. Площадка пилота — по сигналу, не по календарю

- Хостинг в КЗ: self-hosted Supabase в местном облаке или on-prem у заказчика. Нужен runbook развёртывания, бэкапов и restore.
- Мониторинг: Sentry, логи и алерты Supabase.
- Офлайн PWA по §10.5 — только если на площадке пилота нет связи в конторе.
- Казахский язык.
- Лендинг: убрать заявления, которые не подтверждены (on-prem, ERP, «протестированы на реальных сценариях»), или сделать их правдой.

### Вычеркнуть из планов

## 7. Как исполнять

- Каждая фаза — отдельный план в `docs/superpowers/plans/` и шаги Pn.md с гейтами в `tasks/<фаза>/`.
- План, касающийся `supabase/`, начинается с загрузки `supabase-postgres-best-practices`.
- pgTAP — только на `.pgtap-stack`. На живой стенд — `migration up`. Сброс живого стенда — только с подтверждением владельца.
- После фазы 0 ветки идут через PR в `main`, и `/ultrareview` снова можно запускать на каждую фазу.

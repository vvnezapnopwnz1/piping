# Сквозная проверка PipeQC по мануалу Easy Piping: тестовые данные и пошаговый проход

Дата: 2026-10-09. Статус: проект согласован с владельцем в чате, ждёт ревью этого файла.

## Зачем

Владелец хочет, чтобы весь процесс от спулинга до сдачи test pack проходился максимально просто: без лишней логики и без нагромождения проверок. Что считать правильным, определяет первоисточник, а не предположения.

Поэтому сначала проект наполняется тестовыми данными, которые закрывают все проверки. Затем каждый модуль и каждый переход между модулями проходится по шагам и сравнивается с мануалом. Исправления делаются потом, по фактам из журнала.

Анализ `docs/audits/2026-10-09-fabrication-to-test-pack-logic.md` служит входом в эту проверку, а не планом работ:
- Новые функции оттуда отклонены: результат испытания, состояние «сдан», неблокирующие замечания, ворота «выпуск перед выездом», подписанный выпуск ISO, пометка ревизии.
- Находки L1–L5 проверяются на соответствие мануалу во время прохода.

## Первоисточник

- `Easy Piping User Manual.pdf`, 156 стр., v4.7.3; его текст — `docs/marker-output/manual.md`. Главный источник бизнес-правил.
- `docs/research/2026-07-30-easy-piping-documentation-dossier.md` — разбор мануала со ссылками. Канонические вычисляемые состояния — §29, запреты — §30, правило разрешения расхождений — §2.4.
- Презентации (`docs/*.pptx`, `docs/research/presentation_findings*.md`, `test_pack_appendix.md`) уточняют мануал, но не перекрывают его.

`docs/MANUAL_COVERAGE_MATRIX.md` устарела (май 2026, ещё до перехода на Supabase), источником не служит.

## Что считается успехом

1. На локальном стенде есть проект `E2E-1`: у каждого ISO своя роль, вместе роли закрывают все проверки модулей. SHOWCASE-1 и TRACK01 при этом не изменились.
2. Все восемь модулей пройдены в порядке процесса, каждый переход проверен на «сквозной нити».
3. На каждую проверку в журнале есть ссылка на мануал и вердикт. Владелец подтвердил каждый модуль.
4. По сводке журнала можно написать план исправлений, в котором «лишнее» удаляется, а не обрастает новым.

## 1. Проход по модулям

Порядок повторяет процесс в мануале:

1. **Настройка проекта** — справочники, которые нужны дальше.
2. **Спулинг и ревизии** — импорт, валидация, решения по ревизии, просмотр.
3. **Цех** — проверка материалов → сварка → NDE → PWHT → выпуск QC → покраска → Final QC → склад.
4. **Перемещения** — события, текущее место, катушка «в пути», расхождения.
5. **Монтаж** — на площадку → смонтирован → сварено/собрано → закреплено → готов к испытанию; монтажная проверка материалов и монтажная сварка.
6. **Фланцы** — сборка, категории Y/Z.
7. **Test pack** — состав → готовность → проверка линии → замечания X → заглушки → испытание → Y → пусконаладка → Z.
8. **Отчёты** — беглая проверка, что отчёты по модулям открываются и показывают данные `E2E-1`.

Один круг на модуль:

1. Из мануала и разбора выписываются проверки модуля: состояния, переходы, запреты. Каждая проверка — одна строка со ссылкой на раздел.
2. Модуль проходится в видимом браузере на `http://localhost:3000/?p=E2E-1`. Записи в UI делаются только в `E2E-1`.
3. Первым проверяется **переход в модуль** на сквозной нити: появилось ли здесь то, что сделано в прошлом модуле; пришлось ли выбирать объект заново; есть ли путь вперёд.
4. Владельцу показываются скриншоты и таблица вердиктов.
5. Владелец подтверждает или поправляет, после этого переходим к следующему модулю.

По ходу ничего не исправляется, только записывается. Исключение — поломка, без которой дальше не пройти: её обсуждают сразу, и решение записывают в журнал.

## 2. Данные `E2E-1`

У каждого ISO своя роль. Данные должны быть корректны по мануалу: монтажные стыки и опоры записаны до этапов «сварено/собрано» и «закреплено». Где текущая схема не позволяет выразить корректное по мануалу состояние, загрузчик делает то, что позволяют команды, и записывает это ограничение в отчёт загрузки как известную находку. Пример — опора записывается только один раз (`UNIQUE (support_revision_id)`).

| ISO | Роль | Что проверяет |
|---|---|---|
| E-01, E-02 | **Сквозная нить.** На стенд не грузятся; файлы Spoolgen лежат для ручного импорта. | Весь путь от импорта до Z, руками |
| E-03 | Файл с ошибкой: нет правила толщины для класса и диаметра | Блокер импорта, понятность причины |
| E-04 | rev0 загружен, файл rev1 лежит для ручного импорта (изменены стык и катушка) | Решения по ревизии, сохранение истории |
| E-05 | Импортирован, материалы не проверены | Начало цеха |
| E-06 | Сварка выполнена наполовину | Прогресс сварки, WPS, сварщики |
| E-07 | Брак NDE → ремонт → tracer | Цикл NDE |
| E-08 | Толщина выше порога, требуется PWHT, результата нет | Блок выпуска до PWHT |
| E-09 | Всё готово к выпуску, выпуск не записан | Выпуск QC |
| E-10 | Выпущен, отправлен на покраску | Покраска, DFT |
| E-11 | Final QC, склад | Склад |
| E-12 | Катушка «в пути» дольше срока проекта | Transit Out |
| E-13 | Место не совпадает со статусом | Расхождение перемещений |
| E-14 | На площадке, монтажные стыки частично | Монтаж в процессе |
| E-15 | Катушки по мануалу готовы к испытанию, фланцы не собраны | Готовность ISO, фланцы |
| E-16 | В TP-01 вместе с E-14, TP-01 заблокирован | Причины блокировки пакета |
| E-17 | TP-02: проверка линии выполнена, X открыты | Замечания X, Item Clearance |
| E-18 | TP-03: готов к испытанию, заглушки выданы | Заглушки |
| E-19 | TP-04: испытан, ждёт восстановления Y | Y → пусконаладка |
| E-20 | TP-04: доведён до восстановления Z | Конец процесса |

Объём: по 2 катушки на ISO. На каждой катушке цеховые и монтажные стыки, опора, фланцы с категориями Y и Z там, где этого требует роль. История растянута на несколько недель, чтобы графики на сводках были осмысленными.

Справочники `E2E-1` берутся из manifest, плюс то, чего там нет для этих ролей. Пример — правило NDE-матрицы с обязательным PWHT и порогом толщины: в manifest у всех правил `pwhtRequired: false`.

## 3. Загрузчик

- Команда `npm run demo:e2e`; читает `.env.local`, как остальные demo-скрипты. Работает **только с локальным Supabase** и **не сбрасывает базу**.
- Создаёт проект `E2E-1`, доступ тестовых пользователей и справочники проекта. Остальные проекты не трогает.
- Фоновые ISO (E-04 rev0, E-05…E-20) импортирует настоящим импортом Spoolgen (`spoolgen-fixture-import.ts`). Прогресс проводит теми же командами, что вызывает интерфейс, от имени тестового оператора, как `bootstrap-showcase-dataset.ts`. Прямые вставки в таблицы прогресса запрещены.
- Файлы для ручного импорта (E-01, E-02, E-03, E-04 rev1) кладёт в `fixtures/e2e/manual-import/` и описывает в `README` рядом с ними.
- Удалить загруженный проект нельзя: внешние ключи `RESTRICT`, принятые NDE блокируют стыки. Поэтому повторный прогон идёт в новый код проекта: `npm run demo:e2e -- --project E2E-2`. Если проект с таким кодом уже есть, загрузчик отказывается работать и объясняет почему.
- Форма набора данных — какой ISO в какой роли, сколько записей ожидается — описана чистой функцией и покрыта unit-тестом, как `scripts/demo/showcase-dataset.ts`.
- В конце загрузчик печатает отчёт: для каждой роли — ожидаемое состояние и фактическое по view (`spool_fabrication_readiness`, `spool_erection_readiness`, `isometric_readiness`, `test_pack_readiness`), плюс известные ограничения схемы.
- `npm run demo:check` после загрузки в том же состоянии, что до неё. Известный провал — остаток `import_jobs` в `TRACK01-B` — к этой работе не относится.

## 4. Журнал

Файл `docs/acceptance/2026-10-09-e2e-walkthrough.md`.

- Наверху — блок «Где остановились»: последний пройденный модуль, шаг сквозной нити для E-01 и E-02, открытые вопросы к владельцу.
- Раздел на модуль. Строка на проверку: `# | раздел мануала | как должно быть | как есть в PipeQC | вердикт | скриншот`.
- Четыре вердикта:
  - **совпадает**;
  - **нарушено** — PipeQC делает не то, что мануал;
  - **лишнее у нас** — в PipeQC есть шаг, проверка или экран, которого процесс по мануалу не требует;
  - **нет у нас** — мануал требует, в PipeQC нет.
- Скриншоты — `docs/acceptance/e2e/<модуль>-<n>.png`.
- В конце — сводка по вердиктам и модулям. Она станет входом в план исправлений.

## 5. Этапы и сессии

| Этап | Что | Кто | Результат |
|---|---|---|---|
| 0 | Этот файл и план этапа A | Claude | спецификация, план |
| A | Загрузчик, unit-тест, загрузка `E2E-1` | исполнитель (agy/Cline) по плану, Claude проверяет | проект `E2E-1` на стенде, файлы ручного импорта, отчёт загрузки |
| B1 | Настройка, спулинг, ревизии | Claude + владелец | раздел журнала |
| B2 | Цех, NDE, PWHT | Claude + владелец | раздел журнала |
| B3 | Перемещения, монтаж, фланцы | Claude + владелец | раздел журнала |
| B4 | Test pack, отчёты, сводка | Claude + владелец | раздел журнала и сводка |
| C | План исправлений по сводке, выполнение пачками | Claude пишет план, исполнитель делает | исправленное приложение, каждая пачка показана в браузере |

Одна группа модулей — одна сессия. Новая сессия начинается с чтения этого файла и журнала. Журнал коммитится в текущую ветку в конце каждой сессии, без новых веток и worktree.

## Границы

- Не проверяются: роли и права субподрядчика, PDA/офлайн-синхронизация, качество перевода. Непереведённый текст отмечается в журнале одной строкой.
- Схема, правила и интерфейс на этапах A и B не меняются. Единственное новое — загрузчик и его файлы.
- Живой стенд не сбрасывается. `demo:prepare`, `demo:showcase`, `supabase db reset` и `npm run verify` не запускаются (см. CLAUDE.md и память «Keep the live stand»).
- Секреты из `.env.local` не печатаются и не передаются в командной строке.

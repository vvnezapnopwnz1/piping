# Сквозная проверка PipeQC по мануалу Easy Piping: проект как настоящий

Дата: 2026-10-09. Статус: согласовано с владельцем в чате (вариант 3 — вместе по модулям, вариант Б — недели скриптом, нить руками). Ждёт ревью этого файла.

## Зачем

Владелец хочет, чтобы весь процесс от спулинга до сдачи test pack проходился максимально просто, без лишней логики и нагромождения проверок. Правильным считается то, что описано в первоисточнике.

План:
- Завести проект так, как это делает настоящий подрядчик: справочники и спулинг из Excel.
- Провести проект неделя за неделей.
- После каждой недели пройти модули и переходы между ними, сравнивая с мануалом.
- Исправления делать потом, по фактам из журнала.

Анализ `docs/audits/2026-10-09-fabrication-to-test-pack-logic.md` — вход в проверку, а не план работ:
- Новые функции оттуда отклонены владельцем: результат испытания, состояние «сдан», неблокирующие замечания, ворота «выпуск перед выездом», подписанный выпуск ISO, пометка ревизии.
- Находки L1–L5 проверяются по мануалу во время прохода.

## Первоисточник

- `Easy Piping User Manual.pdf`, 156 стр., v4.7.3. Текст — `docs/marker-output/manual.md`. Это главный источник бизнес-правил.
- `docs/research/2026-07-30-easy-piping-documentation-dossier.md` — разбор мануала со ссылками:
  - §29 — канонические вычисляемые состояния;
  - §30 — запреты;
  - §2.4 — правило разрешения расхождений между источниками.
- Презентации (`docs/*.pptx`, `docs/research/presentation_findings*.md`, `test_pack_appendix.md`) уточняют мануал, но не перекрывают его.

`docs/MANUAL_COVERAGE_MATRIX.md` устарела (май 2026, ещё до Supabase) и источником не служит.

Спулинг в мануале загружается четырьмя текстовыми файлами: `weld.txt`, `trace.txt`, `bolt.txt`, `supp.txt` (§13.1). PipeQC принимает ровно их. Поэтому путь «Excel → сохранить как текст с табуляцией → импорт» соответствует мануалу. Загрузка спулинга прямо из `.xlsx` — новая функция, в объём не входит.

## Что считается успехом

1. Есть книга Excel демо-проекта и выгруженные из неё файлы. Проект заводится из них через интерфейс, а импорт проходит проверки без обходных путей.
2. Проект проведён по всем неделям. Каждая ситуация из списка покрытия (§3) встретилась хотя бы раз.
3. Все восемь модулей пройдены, переходы проверены на сквозной нити. На каждую проверку в журнале есть ссылка на мануал и вердикт. Владелец подтвердил каждый модуль.
4. По сводке журнала можно написать план исправлений, в котором «лишнее» удаляется, а не обрастает новым.

## 1. Демо-проект и его файлы

Профиль: «Установка подготовки газа», код `UPG-1`. Ближе всего к пилоту в Казахстане.

| Что | Объём |
|---|---|
| Системы | 3, у каждой подсистемы |
| ISO | около 40; номер линии и класс на ISO единые (§14.1) |
| Катушки | около 100 |
| Стыки | около 500: примерно 3/4 цеховых, 1/4 монтажных |
| Опоры | на каждой катушке |
| Фланцы | категории Y и Z |
| Материалы | углеродистая и нержавеющая сталь |
| Толстостенные линии | требуют PWHT по NDE-матрице |
| Субподрядчики | цеховой и монтажный |
| Test pack | около 6 |

Генератор `npm run demo:project-files` кладёт в `fixtures/demo-project/`:

- **Книга `UPG-1.xlsx`:**
  - листы справочников с Excel-импортом: PML с номерами плавок, WPS, квалификации сварщиков, толщины/фланцы, NDE-матрица. Заголовки совпадают с шаблонами приложения (`modules/imports/domain/import-types.json`);
  - лист «Ввести вручную» — справочники без импорта: системы, подсистемы, классы, PDS-зоны, типы швов, бригады, коды замечаний, места, участки склада;
  - листы спулинга WELD, TRACE, BOLT, SUPP;
  - лист состава test pack;
  - лист README: порядок загрузки.
- **Четыре файла** `weld.txt`, `trace.txt`, `bolt.txt`, `supp.txt`, выгруженные из листов спулинга.
- **Ревизия rev1** для одного ISO: изменены стык и катушка. Импортируется руками на неделе 3, когда катушки этого ISO уже в цеху.
- **Набор с ошибкой:** в одном ISO нет правила толщины для класса и диаметра. Нужен, чтобы увидеть блокер импорта.
- **Файл состава test pack** для импорта.

Номера плавок в TRACE совпадают с PML. Сочетания класса, места сварки и типа шва покрыты NDE-матрицей. Один стык намеренно без покрывающего WPS: мануал требует здесь предупреждение, а не блокер (§14.2).

Форма данных описана чистыми функциями и покрыта unit-тестами по образцу `scripts/demo/showcase-dataset.ts`. Книгу можно открыть, поправить в Excel и выгрузить заново.

## 2. Как проект попадает в базу

1. **Сброс стенда.** `npm run demo:prepare -- --confirm-local-reset` создаёт пользователей. Владелец разрешил сброс для этой работы; перед каждым сбросом Claude всё равно спрашивает подтверждение.
2. **`npm run verify` на пустой базе**, по порядку из CLAUDE.md. Результат записывается в журнал. Известный провал свежего стека (13 тестов привилегий) не блокирует работу.
3. **Через интерфейс, как заказчик:**
   1. «Настройка проекта → Описание»: создать `UPG-1`.
   2. «Доступ»: добавить пользователей.
   3. «Справочники проекта»: ввести формами значения с листа «Ввести вручную».
   4. «Импорт»: загрузить листы PML, WPS, квалификаций, толщин и NDE-матрицы.
   5. «Спулинг → Импорт»: загрузить сначала набор с ошибкой (видим блокер), затем основные четыре файла.
   6. «Test Packs»: импортировать состав.
4. **SHOWCASE-1 после сброса пропадает.** Если он нужен для показов, его восстанавливают `npm run demo:showcase` после `verify`. Решение — в начале B1.

Пункт 3 — это и есть первая сессия проверки (B1).

## 3. Недели стройки

Симулятор `npm run demo:week -- --project UPG-1 --week N` проживает неделю N:
- работает теми же командами, что вызывает интерфейс, от имени тестовых операторов, как `bootstrap-showcase-dataset.ts`;
- прямых вставок в таблицы прогресса нет;
- инженерные данные не создаёт — работает с тем, что уже импортировано;
- ISO сквозной нити не трогает;
- только локальный Supabase.

Повторный запуск недели безопасен: у каждой команды ключ идемпотентности `upg-w<N>-…`.

**Даты.** Проект начался за 8 недель до дня генерации файлов, поэтому даты недели N уже в прошлом. Внутри недели работы разнесены по дням, чтобы графики были осмысленными.

План недель:

| Неделя | Что происходит |
|---|---|
| 1 | проверка материалов, начало цеховой сварки |
| 2 | сварка, первая партия NDE, брак |
| 3 | ремонт и tracer, PWHT, первые выпуски QC; приходит rev1 — импорт руками, решения по ревизии |
| 4 | покраска и DFT, Final QC, склад, отправка на площадку; одна катушка застревает в пути |
| 5 | на площадке: смонтировано, монтажная проверка материалов, монтажная сварка |
| 6 | монтажная сварка и NDE, опоры, сборка фланцев, готовность катушек и ISO к испытанию |
| 7 | проверка линии, замечания X, их закрытие, заглушки, испытание |
| 8 | восстановление Y, пусконаладка, восстановление Z |

Часть пакетов по плану отстаёт, чтобы на каждой неделе были и заблокированные, и продвинутые объекты.

**Список покрытия.** Unit-тест проверяет, что за 8 недель каждая ситуация встречается хотя бы раз:

| Модуль | Ситуации |
|---|---|
| Спулинг | блокер импорта; предупреждение WPS; ревизия ISO во время цеха |
| Цех | частичная сварка; партия NDE; брак → ремонт → tracer; требуется PWHT; выпуск QC; покраска с DFT; Final QC; склад |
| Перемещения | отправка и приход; катушка в пути дольше срока; место не совпадает со статусом |
| Монтаж | монтажная проверка материалов; монтажная сварка и NDE; опоры; готовность катушки и ISO к испытанию |
| Фланцы | сборка; категории Y и Z |
| Test pack | пакет заблокирован выше по процессу; проверка линии с X; закрытие X; заглушки; испытание; Y; пусконаладка; Z |

**Сквозная нить.** Два ISO симулятор не трогает. Их работу за ту же неделю записываем руками через интерфейс, в ногу с остальными. Так проверяются переходы: сделанное в одном модуле появляется в следующем без повторного выбора объекта.

## 4. Проход по модулям

Порядок повторяет процесс в мануале:

1. Настройка проекта.
2. Спулинг и ревизии.
3. Цех.
4. Перемещения.
5. Монтаж.
6. Фланцы.
7. Test pack.
8. Отчёты — беглая проверка, что отчёты показывают данные `UPG-1`.

Цикл недели:

1. Claude запускает `demo:week` для недели N и показывает отчёт: что сделано и какие ситуации появились.
2. Работы недели по сквозной нити записываются руками.
3. Проходятся модули, которых коснулась неделя.
4. Для каждого модуля сначала проверяется переход в него, затем сам модуль: состояния, действия, запреты.

Проверки модуля выписываются из мануала в начале первой недели, где модуль появляется.

После каждого модуля Claude показывает владельцу скриншоты и таблицу вердиктов, владелец подтверждает или поправляет.

По ходу ничего не исправляется, только записывается. Исключение — поломка, без которой дальше не пройти: её обсуждают сразу, решение записывают в журнал.

## 5. Журнал

Файл: `docs/acceptance/2026-10-09-e2e-walkthrough.md`.

- **Наверху — блок «Где остановились»:** последняя прожитая неделя, шаг сквозной нити, открытые вопросы.
- **Раздел на неделю, внутри — по модулям.** Строка на проверку: `# | раздел мануала | как должно быть | как есть в PipeQC | вердикт | скриншот`.
- **Вердикты:**
  - «совпадает»;
  - «нарушено» — PipeQC делает не то, что мануал;
  - «лишнее у нас» — шаг, проверка или экран, которых процесс по мануалу не требует;
  - «нет у нас» — мануал требует, в PipeQC нет.
- **Скриншоты:** `docs/acceptance/e2e/w<N>-<модуль>-<n>.png`.
- **В конце — сводка** по вердиктам и модулям. Это вход в план исправлений.

## 6. Этапы и сессии

| Этап | Что | Кто | Результат |
|---|---|---|---|
| 0 | Этот файл и план этапа A | Claude | спецификация, план |
| A | Генератор файлов, симулятор недель, unit-тесты. Проверочный прогон: сброс → загрузка `UPG-1` из файлов скриптом теми же командами импорта → недели 1–8 → отчёт покрытия | исполнитель (agy/Cline) по плану, Claude проверяет | файлы в `fixtures/demo-project/`, доказанный прогон |
| B1 | Сброс, `verify`, заведение проекта через интерфейс, спулинг | Claude + владелец | журнал: настройка, спулинг |
| B2 | Недели 1–4: цех, NDE, PWHT, ревизия, перемещения | Claude + владелец | журнал |
| B3 | Недели 5–6: монтаж, фланцы | Claude + владелец | журнал |
| B4 | Недели 7–8: test pack до Z, отчёты, сводка | Claude + владелец | журнал и сводка |
| C | План исправлений по сводке, выполнение пачками | Claude пишет план, исполнитель делает | исправленное приложение, каждая пачка показана в браузере |

Зачем проверочный прогон в этапе A: до сессии с владельцем убедиться, что файлы проходят настоящий импорт, а все 8 недель проходят командами без отказов. Скриптовая загрузка в прогоне повторяет шаги B1, но на них не заменяет: в B1 то же самое делается руками через интерфейс.

В прогоне скрипт делает и то, что в проходе делается руками:
- применяет rev1 вместе с решениями по ревизии теми же командами, что вызывает Revision workbench;
- проводит сквозную нить симулятором с флагом `--include-thread`.

Так доказывается, что весь путь проходим до Z.

Если команда отказывает, потому что текущие правила не дают записать корректное по мануалу состояние, симулятор не обходит отказ. Он записывает его в отчёт как известную находку. Пример — опора записывается только один раз (`UNIQUE (support_revision_id)`).

Одна сессия — один этап B. Новая сессия начинается с чтения этого файла и блока «Где остановились» в журнале. Журнал коммитится в текущую ветку в конце каждой сессии, без новых веток и worktree.

## Границы

- **Не проверяются:** роли и права субподрядчика, PDA/офлайн-синхронизация, качество перевода. Непереведённый текст отмечается в журнале одной строкой.
- **На этапах A и B меняются только скрипты демо-данных и их файлы.** Схема, правила и интерфейс приложения не меняются.
- **Сброс стенда допустим только для этой работы и только после подтверждения владельца в момент сброса.** Hosted-стенд не трогается.
- **Секреты** из `.env.local` не печатаются и не передаются в командной строке.

# N3: время применения спулинга при размере пилота

Дата 17.10.2026, локальный стенд (PostgreSQL 17.6), роль `authenticated` с лимитом 8 с. Воспроизведение:
`npm run demo:time-import -- --copies 5 --per-job 5` (создаёт измерительный проект `PERF-1`, копирует 40 ISO проекта UPG-1 под другими номерами).

## Что было

Импорт R0 проекта UPG-1 (40 ISO, 94 катушки, 577 стыков) применялся за 7,7 с при лимите 8 с (фаза 2, B1). На KZ он не укладывался даже
при 30 с. У пилота 5–15 тысяч стыков.

## Куда уходило время

`pg_stat_user_functions` (`track_functions = all`) на импорте в 40 ISO, 4,7 с после первого исправления:

| Функция | Вызовов | Время, мс |
|---|---|---|
| `preview_spooling_import` | **328** | 4 317 (из них 4 722 — всё применение) |
| `spooling_staging` | 462 | 227 |
| `recompute_fabrication_spool_projection_now` | 94 | 45 |

До первого исправления проекция катушки пересчитывалась по строке (около 1 200 раз по 16 мс). Диф ревизий пересчитывался на каждую катушку
и на каждый вид потомков.

## Что изменено

| Миграция | Что |
|---|---|
| `20261018108000` | Пока применяется импорт, пересчёт проекции только помечает катушку; обёртка пересчитывает каждую помеченную один раз в конце той же транзакции |
| `20261018109000` | В списке удаления добавлено `where true`: роли API работают с `pg_safeupdate`, суперпользователь в pgTAP этого не видел |
| `20261018110000` | Диф читается один раз в временную таблицу и дальше из неё (328 вызовов вместо одного) |
| `20261018111000` | Размещённые строки BOM читаются один раз |

Те же строки записываются: диф ISO фиксирован до начала его прохода. Весь набор pgTAP (71 файл, 1 173 теста) зелёный; тест `124` фиксирует форму.

## Результат

Применение (только команда `apply`, без валидации):

| Импорт | Было | Стало |
|---|---|---|
| 40 ISO, 577 стыков | 7,7 с | 0,7 с (после `…110000`; после `…111000` не замерялось отдельно) |
| 200 ISO, около 2 900 стыков, одна задача | около 38 с (оценка по линейному росту) | **1,7 с** |
| 480 ISO, около 6 900 стыков | не измерялось | **3,6 с** |
| 1 000 ISO, около 14 400 стыков | не помещалось (валидация обрывалась по таймауту) | **8,0 с** |

Импорт размера пилота (до 5 000 стыков) укладывается в 8 с локально. Для KZ коэффициент к локальному у вьюх с проверками прав был около 8,
у `SECURITY DEFINER` команды apply он должен быть ниже; замера на KZ нет.

## Находка: цена чтений растёт с размером всей базы, а не проекта

Когда в базе оказалось около 40 тысяч стыков `PERF-1`, чтения проекта UPG-1 (40 ISO) перестали укладываться в 8 с:
`isometric_readiness`, `test_pack_readiness`, `test_pack_workflow`, `test_pack_document_rows`, `nde_register_rows`.
Раньше те же чтения занимали 0,2–0,9 с. Повторил на 480 лишних ISO (около 7 000 стыков): `isometric_readiness` 0,19 с → 1,8 с,
`test_pack_workflow` 0,5 с → 7,4 с.

**Почему.** План `isometric_readiness`: CTE `current_revision` материализуется для всех проектов, а агрегаты по катушкам, фланцам, проверке
линии считаются для всех ISO базы и только потом встречают фильтр `project_id`. В `test_pack_readiness`, `test_pack_workflow`,
`test_pack_document_rows` та же картина через соединения. Отдельно стоит пол из RLS: набор видимых катушек и изометрик читается
по всей базе (около 60 мс на каждые 500 ISO в каждой политике).

**Что пробовал и откатил (миграции `…112000`–`…119000`, откат `…120000`).** Проект как ключ группировки и условие соединения в каждой
фактовой выборке, чтобы фильтр доходил до агрегатов. С чужим проектом в базе это дало `isometric_readiness` 1,8 → 0,55 с,
`test_pack_workflow` 7,4 → 2,5 с, `test_pack_document_rows` с таймаута до 1,4 с. Но без чужого проекта `test_pack_readiness` стал
0,24 → 0,8 с, а `test_pack_workflow` перестал укладываться в 8 с: соединение по `project_id` делает вьюху параметризованной внутренней
стороной вложенного цикла, и `isometric_readiness` считается заново на каждый ISO пакета (40 циклов в плане). Стоимость растёт
с квадратом размера проекта. Вьюха без параметров проект пробросить надёжно не может, поэтому прежние определения возвращены
(`…120000`); осталась только лишняя колонка `project_id` в `flange_joint_readiness`.

**Решение, которое оказалось не нужным (см. N5).** Хранимая готовность изометрики (проекция, как `fabrication_spool_projections` для катушек): таблица по ISO с
фактами и вердиктом, обновляемая теми же триггерами, и вьюхи `test_pack_*` читают её простым соединением с индексом по проекту.
Тогда чтение проекта стоит строк проекта, а не базы. Входит в фазу 4 (объём) как отдельный план с pgTAP на «те же строки».
`nde_register_rows` и `weld_log_rows` уже зависят от одного проекта по числу строк, но их RLS-пол остаётся.

Для пилота с одним большим проектом и несколькими демо-проектами это приемлемо; для нескольких больших проектов в одной базе нет.

## Находка: на проекте пилотного размера экраны тест-пакетов не открывались

Проект `PERF-1` на 480 ISO (около 7 000 стыков) с 20 тест-пакетами по 24 ISO, чтение самого этого проекта (`npm run demo:read-timings -- --project PERF-1`):

| Чтение | Было | После `…121000` |
|---|---|---|
| `isometric_readiness` | 1,7 с | 2,2 с |
| `test_pack_readiness` | **таймаут (20 с в плане)** | 2,4 с |
| `test_pack_workflow` | **таймаут** | 4,2–6,8 с |
| `test_pack_document_rows` | **таймаут** | 4,4–5,1 с |

Причина: `test_pack_readiness` считал `isometric_readiness` заново на каждый пакет (вложенный цикл с параметризованной внутренней стороной:
20 циклов по секунде). Миграция `20261018121000` считает готовность изометрик один раз за запрос (материализованный CTE). Экраны теперь открываются,
но запас мал: при 2,2 с на 480 ISO и 4,5 мс на ISO проект в 3 000 ISO упрётся в 8 с, а на KZ чтения с проверками прав медленнее в разы.
Основная цена `isometric_readiness` — проверки RLS на каждой катушке и каждом фланце (около 1 мс на катушку, пять проходов).

**Что делать дальше (отдельный план).** Хранимая готовность изометрики плюс хранимое состояние пакета по образцу `fabrication_spool_projections`,
`test_pack_*` читают их простым соединением. Выбор, который нужен владельцу: сейчас счётчики вьюхи считаются по тем строкам, которые читающему
разрешает RLS (для субподрядчика или PDS-зоны это неполные числа); хранимая готовность даёт полные числа тем, кто видит ISO.

## N5: RLS считает право на проект один раз за запрос (миграция `20261018122000`)

Главная цена чтений была в политиках: 128 политик вызывали `current_user_has_capability(project_id, '…')` для каждой строки, а функция
соединяет шесть таблиц. Рецепт из Supabase RLS guide: не звать функцию построчно, а сравнивать со множеством, которое Postgres строит один раз.
`private.user_project_ids('cap')` возвращает проекты, где у пользователя есть право (та же функция по каждому проекту, их единицы), а политики
проверяют `project_id IN (SELECT private.user_project_ids('cap'))`. Предикат тот же: строка видна ровно тогда, когда видна была раньше.
Переписаны 96 политик (все с простым `project_id`); `spool_revisions` (проект через функцию) и проверки PDS-зоны оставлены. Весь набор pgTAP
(включая тесты прав субподрядчика и PDS) зелёный, тест `126` считает, что построчных вызовов не осталось.

Чтение проектов (REST, медиана, локально):

| Чтение | UPG-1, было | UPG-1, стало | PERF-1 480 ISO, было | PERF-1 480 ISO, стало | PERF-1 2 400 ISO |
|---|---|---|---|---|---|
| `isometric_readiness` | 190 мс | **80 мс** | 2,2 с | **0,24 с** | 1,4 с (отдано 1 000 строк из 2 400) |
| `test_pack_readiness` | 240 мс | **90 мс** | 2,4 с | **0,38 с** | 1,6 с (100 пакетов) |
| `test_pack_workflow` | 0,5–0,9 с | **180 мс** | 4,2–6,8 с | **0,55 с** | 2,5 с |
| `test_pack_document_rows` | 0,6–1,0 с | **150 мс** | 4,4–5,1 с | **0,65 с** | 2,8 с |
| `nde_register_rows` | 0,7 с | **110 мс** | — | — | (с чужим проектом на 34 000 стыков: 4,9 с) |
| `weld_log_rows` | 0,9 с | **260 мс** | 1,7 с | **0,23 с** | 0,39 с |

Итог: проект пилотного размера (480 ISO, около 7 000 стыков) открывает все экраны тест-пакетов быстрее 1 с, а проект в пять раз больше — за 3 с.
Хранимая готовность изометрики, описанная выше, больше не нужна для пилота; к ней возвращаемся, если проект перерастёт 3–5 тысяч ISO.
Остаётся межпроектная зависимость агрегатов (`nde_register_rows` с чужим проектом на 34 000 стыков — 4,9 с) и построчные проверки PDS-зоны.

## Очистка

`PERF-1` удалён с локального стенда целиком (все строки по цепочке внешних ключей, объекты хранилища); количество строк остальных проектов
(UPG-1, SHOWCASE-1, TRACK01-A/B) сверено до и после и совпало. Чтения UPG-1 вернулись к прежним значениям.

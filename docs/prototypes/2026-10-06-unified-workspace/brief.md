# PipeQC: три детальных интерактивных UX-концепции

Работа одобрена пользователем: сначала показать разные варианты в браузере, не менять действующее приложение. Ты — Gemini через agy, автор конкретной концепции. Это прототип для выбора UX, а не рабочая интеграция и не новый план. Нужно реально создать и связать экраны в автономном HTML/CSS/JS.

## Границы

Читай только этот brief, reference.md рядом и свой task.md. Работай только в своей текущей папке a, b или c. Создай index.html, styles.css, app.js, report.md. Не пиши в другие папки. Не используй Git вообще, терминал для сетевых команд, Supabase, credentials, .env, настройки пользователя, никакие реальные API или внешние библиотеки. Не открывай браузер самостоятельно: основной агент проверит и покажет результат. Никаких npm install, сборок, серверов, удаления, deploy. Изображения/иконки — inline SVG или CSS, не emoji. Web fonts можно заменить на аккуратную пару Georgia + системный sans-serif; не делай интерфейс целиком serif. Код JS отдельный, без inline обработчиков и eval, все взаимодействия через события. HTML может содержать SVG, но без внешних ссылок на ресурсы. UTF-8.

## Эстетика

Вдохновение — настоящая страница PipeQC в corpservice: тёплая техническая бумага #f5ead8, поверхности #f9f4ed, ink #201e1d, muted #645c50, line #dcd3c4, sage #728157 / #56633f, terracotta #c67139, charcoal #2e2b25, сетка 22px rgba(32,30,29,.07), моноширинные идентификаторы. Спокойная, дорогая, промышленная B2B-среда. Сетка и стрелки имеют смысл связей, не случайный декор. Ясная типографика, точный ритм отступов, читаемые таблицы, тонкие линии, группировка. Не лендинг, не огромный marketing hero, не фон с фиолетовым градиентом. Нужна высокая детализация рабочего приложения. Варианты отличаются моделью взаимодействия и компоновкой, не только цветом.

## Общий сценарий и демонстрационные данные

Во всех концепциях одна и та же полностью локальная синтетическая ситуация. На каждом экране постоянная компактная полоса «UX prototype · Illustrative data · Not connected to Supabase», с ссылкой ../review/index.html для сравнения. Интерфейс приложения на английском, описание концепции в report.md на русском. Не выдавай модельные цифры за live-данные.

Проекты: P-104 North process unit (EPC contractor Meridian, owner Industrial Works, contract NPU-04); P-207 Cooling water loop (другой проект, 0 spool, 0 NDE records, пустое состояние с понятным действием). Роль на прототипе QC Engineer; настройка Reader должна менять доступные действия и описание доступа. Начальный проект P-104, начальный экран project overview. Отдельная Projects страница с карточками и явным Open project. Везде видно текущий код проекта, есть All projects и return to current project. При выборе другого проекта старые объекты/цифры/подсказки сбрасываются. Browser Back/Forward через hash/history возвращают корректный экран и project/object context; не перехватывай Ctrl/Cmd+L, reload или обычные ссылки наружу.

P-104: 16 spool, 4 at Laydown (25%, не QC release); 1 Ready for Test; 85 NDE obligations, 63 have result recorded (не 74% accepted!), 19 issued awaiting result. Список из 5–6 правдоподобных спулов с ISO, location, stage, NDE blockers, PWHT blockers. Центральный объект SP-1001-A, ISO-1001, revision R0. Материальные строки 3 ident codes с description, quantity, heat/trace; 2 из 3 trace уже заполнены, третий пуст. Local Simulate save меняет только демонстрационное состояние и явно сообщает «Prototype only — no project data was saved».

SP-1001-A: Welded / Bolted recorded, Supported recorded, 1 NDE obligation open, PWHT 0; значит RFT blocked именно NDE. Шов W-04, RT obligation issued, batch RT-006. NDE view сохраняет SP-1001-A и выделяет W-04, не открывает анонимную общую таблицу. Record result открывает форму с report number, examination date, outcome Accepted/Rejected. Rejected требует defect code; правило видно возле поля, не hidden tooltip. Simulate save Accepted закрывает локальное NDE obligation, RFT становится Ready — только демо, без реального QC release. Test Pack TP-014 состоит из ISO-1001 и содержит выбранный spool. Состояние TP рассчитывай согласованно: до решения NDE Awaiting RFT, после Ready for blinding. После локальной записи blinding можно показать следующий допустимый Start testing. Ни одна подсказка не выполняет бизнес-действия.

## Обязательные экраны (data-view атрибут на активном контейнере)

1. overview — рабочее состояние P-104, путь к конкретной работе, не руководство «что делает каждый модуль». Схема если есть — часть навигации, активные разделы совпадают с меню. Не три независимых каталога (chips + большая карта + sidebar).
2. projects — выбор и возврат, работа P-207 пустого проекта.
3. fabrication — подробный список/таблица со спулами, фильтром, поиском, ясным выбором объекта.
4. material — выбранный SP-1001-A, trace fields, visible gate, понятное главное действие, readiness/evidence panel.
5. nde — связанная очередь и выбранное issued RT, форма результата/локальное сохранение, method/status/report данные.
6. rft — readiness выбранного spool: каждый реальный критерий отдельной строкой, один NDE blocker как прямой переход в NDE, после Accepted критерии меняются согласованно.
7. testpack — TP-014, membership, current workflow state и действие только на текущей стадии. Не «Mark RFT» и не непонятные UUID.

Все ключевые переходы должны работать, включая Back to overview, прямую навигацию раздела и возврат к тому же объекту. Поиск спулов реально фильтрует строки; no matches отличается от empty project; clear search восстанавливает данные. Разделы за пределами сценария не выдавай за готовые приложения: либо отключи их с понятной подписью «Outside this prototype», либо убери; никаких dead buttons.

## Контекстная помощь

Help кнопка/«Show hints» на экране открывает один немодальный coach mark, привязанный к реальному контролу. Короткий заголовок + 1–2 предложения + caret/короткая стрелка + Close / Don't suggest again. Не требуется tour при старте, затемнение или бесконечная пульсация. Нельзя скрывать причины disabled, required fields, QC blockers. Помощь можно закрыть Esc, вернуть вручную, отключить предложения, после смены проекта закрыть. На mobile target остаётся видимым, popover не вылезает за края; допускается помощь рядом с target inline. Настройку remember только локально с уникальным storage namespace своей концепции. Кнопки закрытия, формы и меню доступны с клавиатуры, aria-label, visible focus. Избегай семантики tooltip для интерактивного popup с кнопками. Reader не видит активных команд записи, но видит состояние/доступ/полезные переходы. Никаких догадок «ты завис» по таймеру.

## Детализация и самопроверка

Responsive 1440px desktop и 390px phone, минимум 3 содержательных рабочих панели на desktop, хорошие density и hierarchy, рабочие таблицы и состояния, sticky project identity, не горизонтальный скролл всего документа (таблица может скроллиться внутри контейнера). По hover видно, что clickable. Работа без помощи должна быть возможна.

Для проверяемости назначь data-action на основные controls: projects, overview, fabrication, material, nde, rft, testpack, help, close-help, simulate-save. Используй один NAV объект/реестр для названий, routes и selected state; не независимые массивы sidebar и overview. Help и бизнес-state не влияют друг на друга. В data-view всегда одно значение текущего экрана.

В report.md перечисли: суть модели, преимущества и tradeoffs, какие взаимодействия сделаны, все созданные файлы. Не заявляй browser/test verified: основной агент проверит. Самопроверка: синтаксис app.js без eval; ссылки правильные; даты/report label видимы; state resets; ESC; Reader; 390px. Не трать ответ на пояснение как когда-нибудь сделать, создай реальные файлы и закончи.

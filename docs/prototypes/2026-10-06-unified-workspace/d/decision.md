# Decision D — UX-решение

Источники различаются по статусу: **наблюдение по коду** (reference.md), **предложение** (этот прототип), **не проверено**. Утверждений о поведении работающего приложения сверх reference.md здесь нет.

## Единственная модель

**Одна горизонтальная процессная навигация: на overview она раскрыта как карта состояния проекта, в рабочем экране сжата в stage rail; выбранный объект (spool / test pack) остаётся с пользователем при переходах.**

Вертикального sidebar нет. Overview-карта *заменяет* rail (на overview rail скрыта), а не показывается рядом с ней. Rail и карта строятся из одного реестра `NAV`.

## 1. Задачи и наблюдаемые противоречия

Задачи QC-инженера: понять, что блокирует SP-1001-A; записать результат NDE для W-04 / RT-006; убедиться, что TP-014 готов к следующему шагу.

Наблюдения по коду (reference.md, без оценки поведения в браузере):
- `config/navigation.ts` (меню) и `home-control-room-model.ts` (обзор) — две самостоятельные структуры, названия расходятся (Preparation/Spooling, NDE vs NDE Module).
- `app-shell.tsx` держит полный sidebar рядом с обзором, где есть строка модулей, карта процесса и повторяющиеся ссылки.
- NDE на схеме — общая функция двух стадий, в меню — отдельный пункт Construction.
- Часть пояснений — язык реализации («Server-scoped assignment», RPC) и длинные общие абзацы вместо видимого состояния объекта.

Это экспертная гипотеза по коду (оценка понятности 6/10 в reference — не исследование пользователей). Выбор проекта и возврат уже реализованы в работающем приложении; цель прототипа — сохранить и сделать это очевидным, а не «исправить».

## 2. Что взято, что отброшено

- **Горизонтальная процессная навигация (идея варианта B)** — единственная глобальная навигация.
- **Сохранение объекта (идея C)** — SP-1001-A и явный Back при переходах Material → NDE → RFT → Test pack.
- **Очередь внимания (идея A)** — компактный список блокеров на overview с прямыми переходами.
- Отброшено: полный sidebar, module chips, «how-to» на overview, отдельный каталог спулов на overview, NDE как линейная стадия, три панели на каждом экране.

Синтез допустим только потому, что три элемента подчинены одной модели; гибрид «rail + карта + очередь + таблица» одновременно отвергнут.

## 3. Три устойчивые зоны

| Зона | Задача |
|------|--------|
| Идентичность (sticky) | Код/название проекта, **All projects** (смена), **Overview** (возврат), Role, Help; над ней постоянная полоса prototype |
| Процессная навигация | Overview: карта состояния (+ очередь внимания). Рабочий экран: компактная stage rail. Projects: скрыта |
| Рабочая область | Workbench: локальный список объектов → операция → компактное evidence. Лишние панели не выводятся |

Дублирование решено так: один реестр `NAV`; карта и rail — два состояния одной навигации; локальные вкладки (Spool list / Material check) выводятся из того же реестра; список спулов в workbench — выбор объекта, не меню.

## 4. Удалённые конкурирующие входы

1. Sidebar-дерево разделов. 2. Module chips. 3. How-to описания модулей на overview. 4. Каталог спулов на overview. 5. NDE как этап между Erection и Test Packs (теперь shared service рядом с rail, пунктирная связь с Fabrication/Erection). 6. Engineering и Tracking — disabled с подписью «Outside this prototype».

## 6. UX-решения и tradeoffs

1. Overview как карта → потеря «каталога» входов; компенсируется очередью. 2. Rail вместо sidebar → меньше мест для будущих разделов (нужен overflow). 3. Контекст объекта в chip + Back → больше состояния в URL. 4. Shared NDE отдельно от этапов → пользователь должен понять «служба», подпись и пунктир это поясняют. 5. Локальные Simulate-команды вместо реального сохранения. 6. Help по запросу, точка-подсказка без пульсации. Перенос после согласования: реестр → shell → overview → пилотные экраны → помощь (по плану reference).

## 7. Что показывает прототип

Реализовано в локальных файлах этой папки (index.html, styles.css, app.js, report.md): 7 экранов, единый `NAV`, 6 из 16 иллюстративных спулов, trace/NDE/TP-симуляции, Reader, history/hash, Help. После отчёта исполнителя основной агент независимо выполнил structural gate (включая node --check) и предметные browser smoke checks: результаты и ограничения описаны в ../acceptance-checklist.md. Пользовательская валидация отсутствует, интеграции с приложением и Supabase нет, Engineering/Tracking и полный Erection не реализованы, данные иллюстративные.

# PipeQC — эксплуатация production-стенда

**Статус на 17.10.2026:** production развёрнут на собственном сервере. Его
единственный пользовательский адрес — <https://app.piping-qc-work.shop/>.
Прежние Vercel и облачный Supabase-стенд больше не являются production и не
должны использоваться для выпуска, миграций или проверки данных.

Этот runbook описывает обычный выпуск. Он не разрешает сброс базы, смену Auth
настроек или работу с секретами без отдельного решения владельца.

## 1. Границы production

```text
GitHub: main
     |
     +--> /opt/pipeqc                 Next.js в контейнере pipeqc-app
     |          |                     только loopback-порт
     |          +--> /opt/supabase    PostgreSQL, RLS, Auth и API
     |
     +--> edge reverse proxy --> https://app.piping-qc-work.shop/
```

| Зона | Источник истины | Как меняется |
| --- | --- | --- |
| UI, маршруты, клиентские команды, отчёты | Git `main` | проверка → merge → controlled Docker release |
| Схема, RLS, функции, RPC | `supabase/migrations/` | новая forward-миграция с backup и проверкой |
| Учётные записи и бизнес-данные | production PostgreSQL/Auth | штатные команды приложения или отдельно согласованная операция |
| Публичный адрес Auth | конфигурация self-hosted Supabase | отдельная проверяемая операция, затем перезапуск только Auth |

В браузерную сборку попадают только публичный Supabase URL и publishable key.
Пароли базы, JWT-ключи, service-role ключи и резервные копии остаются на
сервере и никогда не попадают в Git, `NEXT_PUBLIC_*`, чат или снимки экрана.

## 2. Обычный выпуск приложения

Сначала на ветке изменений должны пройти релевантные проверки. Для изменения
схемы обязательны pgTAP-тесты; для UI — как минимум unit, typecheck, lint и
production build. После принятия изменения и merge в `main` оператор на
сервере выполняет:

```zsh
cd /opt/pipeqc
git pull --ff-only
sudo docker compose build pipeqc
sudo docker compose up -d --no-deps pipeqc
```

`--no-deps` принципиален: выпуск UI не должен перезапускать PostgreSQL, Auth
или другие приложения на сервере. Затем проверить, что контейнер создан заново
и адрес отвечает по TLS:

```zsh
sudo docker inspect pipeqc-app --format '{{.State.Status}} {{.State.StartedAt}}'
curl -fsSI https://app.piping-qc-work.shop/
sudo docker logs --tail 80 pipeqc-app
```

Статус `200` — технический smoke check, а не приёмка. После него владелец или
назначенный тестировщик проходит изменённый путь в авторизованном браузере.

## 3. Выпуск с миграцией

Никогда не меняйте применённую миграцию: добавляйте новую. Миграция должна быть
совместима с предыдущей версией UI, потому что приложение обновляется после
схемы. Порядок такой:

1. Локально: тест миграции, pgTAP и проверки приложения.
2. На production: подтвердить список pending-миграций и сделать защищённый
   dump PostgreSQL в `/opt/pipeqc/backups/`.
3. Применить только согласованные SQL-файлы в одной контролируемой операции с
   `ON_ERROR_STOP`; зафиксировать их в `supabase_migrations.schema_migrations`.
4. Обновить кэш схемы PostgREST (`NOTIFY pgrst, 'reload schema'`) и проверить
   изменённую таблицу, view или RPC.
5. Выпустить приложение по разделу 2.

Перед destructive-операцией или массовым backfill нужны: проверка, что dump
читается `pg_restore -l`, решение владельца и отдельный план восстановления.
`db reset`, удаление Auth-пользователей и повторное заполнение production для
обычного выпуска запрещены.

Если SQL-изменение не прошло, остановитесь и выпустите корректирующую
forward-миграцию. Откат контейнера не откатывает схему и данные.

## 4. Данные и восстановление

На стенде сейчас сохранён намеренный Curated journey, а не пустой Baseline.
Не переводите его в Baseline и не запускайте `demo:prepare`/`db reset` без
явного согласия владельца на потерю данных.

До внешней приёмки ещё требуются два эксплуатационных доказательства:

- владелец принимает режим данных `TRACK01-A` (Curated journey либо отдельный
  согласованный Baseline);
- сделана и зафиксирована репетиция backup/restore на отдельной среде.

## 5. Нештатные ситуации

| Ситуация | Действие |
| --- | --- |
| Некорректный UI-выпуск | собрать и поднять предыдущий совместимый commit; затем выпустить forward-fix |
| Некорректная миграция | остановиться, исследовать, добавить корректирующую forward-миграцию; не делать reset |
| Не отвечает приложение | проверить `pipeqc-app`, edge proxy и TLS; не перезапускать весь Docker-хост без причины |
| Не отвечает API/Auth | проверить только затронутый self-hosted Supabase-сервис и его логи; данные базы не трогать |
| Нужен возврат данных | действовать по согласованному restore-плану и проверенному backup, с решением владельца |

## 6. Чек-лист выпуска

- [ ] Изменение проверено локально, а миграция — pgTAP-тестами.
- [ ] В `main` есть принятый commit.
- [ ] Для миграции: есть проверяемый backup и список pending SQL-файлов.
- [ ] Обновлён только нужный сервис; база и Auth не перезапускались без причины.
- [ ] `https://app.piping-qc-work.shop/` отвечает по HTTPS, а контейнер новой
      версии работает.
- [ ] Изменённый пользовательский путь проверен в авторизованном браузере.
- [ ] Секреты и backup не попали в commit, публичные переменные или отчёт.

## 7. Передача другому оператору или агенту

Дайте отдельный серверный доступ с минимальными правами, а не личные пароли,
SSH-ключи или `.env` владельца. До mutation оператор сообщает точный commit,
сервисы и миграции, которые будут затронуты. После — commit, список
применённых миграций, время нового контейнера, результат HTTPS smoke check и
отдельный результат браузерной приёмки.

Локальный Supabase MCP относится только к локальному development-стеку. Он не
является production и не заменяет SSH-операции, backup или release-проверку.

# Track 06 Browser Fixtures Runbook

## Overview

`npm run bootstrap:track06-browser-fixtures` builds the **NDE population** a Track 06
walkthrough needs: a second isometric of twelve shop joints, welded by their own pair of
welders, every joint already carrying a pending 10 % RT obligation.

Track 05's fixture cannot do this. It has three joints, and Track 06's mechanics need more:
a spot batch needs something to sample, the NDE100 escalation needs four rejections in one
batch, and each rejection consumes up to two further joints as tracers. Twelve is the
smallest population where all of that fits with joints to spare.

### Prerequisites

Run the previous track bootstraps in order, with the same `TRACK01_FIXTURE_PASSWORD`:

1. `npm run bootstrap:track01-browser-fixtures`
2. `npm run bootstrap:track03-browser-fixtures`
3. `npm run bootstrap:track04-browser-fixtures`
4. `npm run bootstrap:track05-browser-fixtures`

Track 06 reuses Track 05's subcontractor `SUB-T5` and procedure `WPS-T5`, and fails with a
message naming them if the Track 05 bootstrap has not run.

### Usage

```bash
SUPABASE_URL=http://127.0.0.1:54321 \
SUPABASE_SERVICE_ROLE_KEY='<local service-role secret>' \
SUPABASE_PUBLISHABLE_KEY='<local publishable key>' \
TRACK01_FIXTURE_PASSWORD='<same value used for Track 01>' \
npm run bootstrap:track06-browser-fixtures
```

Expected output on a clean database:

```text
Track 06 welders reconciled: 2 welders and 2 WPS links in project <uuid>.
Engineering definition imported: 15 rows applied to ISO-T6-001.
Weld progress recorded on 12 of 12 Track 06 joints; 12 NDE obligations now exist on ISO-T6-001.
```

A second run prints the same first line, then:

```text
Engineering definition ISO-T6-001 already has an accepted revision; nothing to import.
All 12 Track 06 joints already carry weld progress; nothing to record.
```

### Provisioned fixtures

| Object | Value |
| --- | --- |
| Welders | `W-T6-1` (root), `W-T6-2` (cap), both under `SUB-T5`, both linked to `WPS-T5` |
| Isometric | `ISO-T6-001` revision `R0` (accepted), PDS area `PDS-T4`, service class `SC-T4` |
| Spool A | `SP-T6-001-A` — shop welds `W-T6-001` … `W-T6-006`, bill line `IDN-T5-100` |
| Spool B | `SP-T6-001-B` — shop welds `W-T6-007` … `W-T6-012`, bill line `IDN-T5-200` |
| Joints | all `BW-T4`, `shop`, 6″, **6.0 mm** |
| Obligations | 12 × RT, 10 %, `spot`, `pending`, manual status `S` |

### Four fixture decisions and why

1. **Its own welders.** The NDE100 escalation is keyed on `(project, welder)` and rewrites
   every remaining spot obligation that welder owns. Sharing `W-T5-1` would let a Track 06
   escalation reach into the Track 05 golden path and change what `/fabrication/qc-release`
   demands of `SP-T4-001-A`. `bootstrap-track06-browser-fixtures.test.ts` asserts the two
   sets stay disjoint.

2. **6.0 mm, below the PWHT threshold.** The Track 05 bootstrap sets the `SC-T4`/`BW-T4`/
   `shop` rule to `pwht_required = true` with an 8 mm threshold. At 6.0 mm no Track 06 joint
   generates a PWHT requirement, so this population is purely about NDE and the PWHT gate
   stays proven where it already is — on `SP-T4-001-A`'s 8.2 mm joints.

3. **The same matrix rule as Track 05.** Same service class and weld type, so the rule that
   already exists applies and every obligation starts at RT 10 % `spot`. No new referential,
   nothing to keep in step.

4. **A bill of materials, one line per spool.** `spool_fabrication_readiness` treats a spool
   with no bill as never material-checked — `line_total > 0` is explicit in the view. A
   weld-only fixture put *"0 of 0 bill lines traced"* on the QC release screen, which reads
   like a defect and is the rule working. One line per spool makes the sentence honest.

### The welds are recorded by the script, not the browser

Twelve joints at six fields each is not a browser task, and it is not what the Track 06 walk
is testing. The script drives `record_weld_progress` — the same RPC the weld progress screen
calls — as `track01.project-admin-a@example.test`, so the obligations are generated by
`generate_weld_obligations` from the matrix rule rather than inserted behind it. What the
browser walk then covers is the NDE work itself: batches, allocation, results, repairs,
tracers and the escalation.

All twelve joints share one weld date, so `allocate_nde_batch_candidates`, which orders by
`(weld_on, weld_number)`, allocates in weld-number order and nothing else. That is what lets
the walkthrough name the joints it expects to be selected.

### Protection guards

1. **Localhost guard** — the script refuses to run against a non-local Supabase URL.
2. **Idempotency** — welders are upserted; the import is skipped once an accepted revision
   exists; joints that already carry a weld progress record are skipped. Two consecutive runs
   leave identical state.
3. **Real guards, not the service key** — the import and every weld run as the fixture
   project admin through the normal RPCs, so the bootstrap cannot produce state the browser
   could not have produced.
4. **Secret protection** — every secret comes from an environment variable.

### Fixtures and pgTAP do not coexist

Unchanged from Track 05: `supabase db reset` before `supabase test db`, and re-run the
bootstrap chain afterwards if you want the browser fixtures back. Bootstrap data breaks
pgTAP, never the reverse.

### After `supabase db reset`, wait for auth

`db reset` restarts the containers, and the Track 01 bootstrap fails with a `findOrCreateUser`
stack trace if it runs before GoTrue is listening. It is a race, not a defect: re-run the
same command and it succeeds. Check `supabase status` first if you want to avoid the retry.
